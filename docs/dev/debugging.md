# Debugging: demo data, examples, the mock model, scripted windows

Moved out of `CLAUDE.md`. Always combine a manual run with `WISP_STUDY_HOME` so the real library is not touched.

## Demo data

Demo data: `cargo run -p wisp_core --example seed -- /tmp/wisp-demo some.pdf`, then `WISP_STUDY_HOME=/tmp/wisp-demo cargo run`. Further PDFs after the first become papers of the second library with their full text, which is what 写作 needs.

## A PDF that comes out wrong

A PDF that comes out wrong: `cargo run -p wisp_core --example structure -- a.pdf [blocks|sentences|pages|outline|captions|apply reply.txt]` prints what the reader and the structuring make of it (its language, how many paragraphs the rules guessed and whether a model is worth asking, sentences per part; every block with its label; every sentence kept; the page text; the outline a model is asked about; the captions of figures and tables each page shows, as the figure library reads them; the parts a model's answer gives).

## A Word file that comes out wrong

A Word file that comes out wrong: `cargo run -p wisp_core --example docx -- a.docx [same|edit|track out.docx]` prints the paragraphs, headings and comments the reader finds; with a mode it writes the file again (unchanged; with paragraphs changed, taken out and put in and comments added; the same as tracked changes) and says whether the result reads back as what was wanted. LibreOffice is the independent check: `soffice --headless --convert-to pdf out.docx` (or `docx:"MS Word 2007 XML"`, and read that again).

## The mock model (no API key)

No API key at hand: `cargo run -p wisp_core --example mock_model -- 8787` is a fake Claude endpoint: in a chat it calls two tools and then answers (saying how many pictures it was sent, and adding a dozen paragraphs, a list and a table for a question containing 「试试长回答」; a question containing 「试试撤销」 makes it call `undo_import`, which the window asks about first, one containing 「试试连接器」 the first tool of a connector that the request offers, one containing 「试试整理」 `organise_papers` for the first two papers; in the conversation that writes a manuscript, 助手写, it calls `edit_section` and puts a paragraph citing `[P1]` at the end of the section on show, or `set_outline` with three sections for a question containing 「试试大纲」), asked for search queries by the guide it proposes two for PubMed, asked to screen a paper it decides by one word, asked by 写作 for search words it gives three groups, asked by the figure library about a picture it gives a legend, tags or a reading, asked by 配引用 for search words it hands each sentence back and asked which papers bear the sentences out it takes the first found for each (for a sentence containing 「试试转述」 it says that paper only restates it), asked which sentence of a paper a citation rests on (出处) it takes the first offered (none for a citing sentence containing 「试试没有」), asked to review a section of a manuscript (批注) it proposes a change to the first sentence and makes one remark on words that are not there, told to change a section (改稿) it answers piece by piece with blocks that add to the first sentence, ask for words the section does not have, change the start of the last paragraph and put a sentence at the end (two paragraphs for an empty section), asked what a paper's custom fields should hold (提取) it answers each field by its kind and quotes the start of the abstract (for a paper whose text says "Few-Shot": a Select answer that is none of the options and a quotation the paper does not hold), asked to translate (with the default instructions) it hands the text back marked as translated, and asked for a picture (生图) through any of the three interfaces it draws one of the shape asked for, coloured by the description (one containing 「试试失败」 is refused), and asked the way a model that judges is asked (a System One request to `/v1/systemone`) it answers each choice with probabilities: sure of a paper that mentions Arabidopsis, torn about one that mentions a root, sure the rest are irrelevant. A second argument (`-- 8787 1500`) delays every answer by that many milliseconds, to watch a screening run; each request is printed with its model and thinking setting. Point a profile in the demo folder's `settings.json` at `http://127.0.0.1:8787` and drive the window with `WISP_STUDY_DEV=open:0,page:ask,ask:<question>`.

A step written `8@shot:/tmp/a.png` is taken eight seconds after the start, so a script can wait for an import or an answer. The window does not take focus when it is set. `theme:` is saved to `settings.json`, so combine it with `WISP_STUDY_HOME`.

A window that is not on screen draws no frames: in a scripted run, pointer steps need a `shot:` before them, or there are no hitboxes to hit. For the same reason the first `shot:` after a list changed can catch its new rows at the start of their fade-in (`ui::fade_in`), drawn at no opacity: cards missing between cards that were there before are that, not a gap in the layout. Take a second shot a second later before reading anything into it.

## Progress previews

Progress previews in an isolated demo library, without network requests or imported files: `fetch-preview` / `fetch-preview:empty|stopped|complete`, `import-preview` / `import-preview:complete`, and `zotero-preview` / `zotero-preview:complete`. Use `fetched`, `report`, or `zotero-report` to open each live dialog; delayed preview steps can exercise updates while a dialog stays open. These only populate in-memory progress state in debug builds.

## The release check

`WISP_STUDY_UPDATE_URL` points the release check at another address (it must answer with a redirect to this project's release page). `WISP_STUDY_UPDATE_FILES` is the folder the package and its `SHA256SUMS` are then fetched from. The whole update can be rehearsed on macOS without a release: a bundle (`X/Wisp Study.app/Contents/MacOS/wisp_study` from `target/debug`, an `Info.plist` with another `CFBundleIdentifier`, `codesign --force --sign -`), a DMG of a copy of it named `WispStudy-v99.0.0-macos-<arm64|x64>.dmg` beside its `shasum -a 256` as `SHA256SUMS`, and a local server whose `/latest` redirects to `…/releases/tag/v99.0.0`; run the bundle's binary with both variables and `WISP_STUDY_HOME`, and `40@submit` answers the question (a build run from `target/` is not a bundle and is only told of the release). The step `restore` goes back to where `session.json` says the window was, which a scripted start otherwise does not.
