# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Wisp Paper is a local-first literature library desktop app (collect papers, organise, preview PDFs, ask an LLM about the library), written in Rust with GPUI. Targets Windows and macOS; Linux compiles but is untested. The desktop UI supports Chinese and English (Settings › General). Use `i18n::t` with Chinese keys in `locales/en.json` for static labels, and `tf!` with both Rust format literals for dynamic messages. Translate shared label tables at display sites; keep stored keys, user content and model prompts unchanged. Code comments are in English.

## Commands

```sh
cargo run --release                     # run the app
cargo test                              # all four crates (workspace default-members)
cargo run -p wisp_cli -- help           # the `wisp` command line; `-- mcp` is the MCP server
cargo test -p wisp_core                 # engine only; no GPUI build, much faster
cargo test -p wisp_core store::         # one module's tests
cargo test -p wisp_core <test_name>     # one test
cargo test -- --ignored lookup          # live Crossref / Europe PMC lookups (network)
cargo clippy --all-targets              # expected to be warning-free
```

- The toolchain is pinned in `rust-toolchain.toml` (clippy only). There is no rustfmt component and no `rustfmt.toml`: the code is hand-formatted with long lines and one-line `if x { return }` bodies. Do not run `cargo fmt`; match the surrounding style.
- Windows needs the MSVC build tools.
- CI (`.github/workflows/ci.yml`) runs clippy with `-D warnings` and the tests on Windows and macOS, and the three windowless crates on Linux. A release is a pushed tag `v<version>` that matches the version in `Cargo.toml` (`release.yml`; notes from `.github/release-notes/v<version>.md`). It is always signed, the way BiblioCell does it: `scripts/package-macos.sh --arch universal` builds, signs with the Developer ID certificate, notarizes and staples the app and the DMG; `scripts/package-windows.ps1 -Sign` signs both exes through SSL.com eSigner (`scripts/sign-windows-esigner.ps1`); Linux is an unsigned tar.gz. The ten secrets are listed at the top of `release.yml`; with one missing the run stops before building. A pull request touching `scripts/` or the workflow rehearses the packaging unsigned. Locally `CARGO="cargo +stable" scripts/package-macos.sh` gives an ad hoc signed `dist/Wisp Paper.app`.
- Demo data: `cargo run -p wisp_core --example seed -- /tmp/wisp-demo some.pdf`, then `WISP_PAPER_HOME=/tmp/wisp-demo cargo run`. Further PDFs after the first become papers of the second library with their full text, which is what 写作 needs.
- A PDF that comes out wrong: `cargo run -p wisp_core --example structure -- a.pdf [blocks|sentences|pages|outline|captions|apply reply.txt]` prints what the reader and the structuring make of it (its language, how many paragraphs the rules guessed and whether a model is worth asking, sentences per part; every block with its label; every sentence kept; the page text; the outline a model is asked about; the captions of figures and tables each page shows, as the figure library reads them; the parts a model's answer gives).

## Architecture

A Cargo workspace of four crates. Dependencies point one way only: `wisp_net` depends on core, the app and the command line depend on both.

### `crates/core` (`wisp_core`): the engine, no GPUI

Everything that can be decided without a window or a socket lives here, and it is where nearly all tests are. That includes the pure halves of networked features: `lookup` builds Crossref / Europe PMC URLs and turns their JSON into a `Paper`; `ai` builds the context, the request body for the three protocols (Anthropic Messages, OpenAI-compatible chat completions, OpenAI Responses) and parses stream lines into `StreamEvent`s. The actual HTTP (blocking `ureq`) is in `crates/net` (`wisp_net`), shared by the app and `wisp`; its tests serve canned responses from a local port. Code in core that needs the network takes the fetching function as an argument (`sources::Fetch`), so core tests pass a closure.

On-disk layout: the data root holds one folder per library, each with `library.json` (`libraries`), `wisp-paper.sqlite` and `papers/` (`store`). Attachment paths in the database are relative to the library folder so a folder can be copied elsewhere. Removing a library or attachment moves it to `removed/`; nothing is deleted.

`store.rs` notes:
- The schema is one `CREATE TABLE IF NOT EXISTS` batch guarded by `SCHEMA_VERSION` / `PRAGMA user_version`; a newer database is refused. Bump the version when an older build would misread the data.
- Deduplication is by DOI, PMID (`paper_identifiers`), then `title_key`. Trashed papers stay in `papers` (marked by a `trashed_papers` row) so they keep blocking re-import.
- `Store::in_memory` is what tests use.
- `Paper::fulltext` is computed, not stored: `missing`, `linked`, `stored`, or `textless` (a full-text file is there and no text came of any). Why a file gave no text is the sentence kept in `fulltext_text.error`; `fulltext::failure_kind` tells the kinds apart (`locked`, `parser`, `encoding`, `no_text`, `file`, `unsupported`), messages of earlier builds included, and a new reason is a constant there, not a string somewhere else.
- Status values are stored as English keys and shown through the label tables in `model.rs` (`SCREENINGS`, `READINGS`, …). The labels are not translations: the stored key `excluded` is displayed as 「相关」.

`figure.rs` is 图片库: pieces cut out of PDF pages and kept as pictures under `figures/` in the library folder, one `figures` row each (number, legend, notes, tags of their own, and the paper, file, page and box they came from). The table is made beside the library's own like the manuscripts'; no version bump. `caption` finds the caption a piece belongs to among the page's lines (`pdftext::lines`): a line that `opening` takes for a caption's start (`Fig. 2 |`, `Figure 3.`, `Table S1`, `Extended Data Fig. 4`, `图 3`; not running text that begins `Figure 2 shows` or `Fig. 2a). These`), the nearest within `REACH` that shares the piece's columns (a figure's under it, a table's over it), read on through the lines set alike under it. `Ask`, `ask_prompt` and `read_legend` / `read_tags` / `read_notes` are what a model that sees the picture is asked and how its answer is read. A figure is listed while its paper is outside the trash; `delete_paper` and `remove_figure` set the picture aside in `removed/`. Tool: `list_figures` (read-only).

`tools.rs` is the one table of what an agent can do with a library; the command line, MCP and (next) the in-app assistant all end in `tools::call`, so a rule belongs there and not in a front end. `ai.rs` holds the model side of the loop: the request with tool definitions for each protocol, `TurnReader` (one streamed turn → text, tool calls, the message to send back), `tool_results`, and the slash commands (`SLASH`: the prompt templates behind `/search`, `/cite`, `/review`, `/compare` and `/write`).
- A new tool is an entry in `catalog()` (name, Chinese description, JSON Schema) and an arm in `call_in`. Nothing else: `wisp <tool>` reads its flags off the schema (`cli_args`), and `mcp::handle` lists and calls whatever the catalog holds. The test `every_tool_is_callable` fails when an entry has no arm.
- Tools take `library` (id or name, optional when there is one library) and return JSON; an error is a Chinese sentence for the caller, person or model.
- Screening is against the library's goal (`LibraryInfo::criteria`, 筛选目标; empty means by the topic), saved as it is typed. Each suggestion keeps the goal it was made against (`screening_suggestions.criteria`, NULL for one from before, which counts as current; `Suggestion::made_for`); one made for another goal is shown as 按旧目标 and asked again by the next run. 复核 (`Cmd::ScreenRecheck`) asks about the decided papers too: one the assistant now sees otherwise comes back to the queue (`Library::rechecking`, until the person decides it again, which keeps or changes the decision), the decision itself is never touched. Columns added later go through `store::add_columns`.
- A suggestion never writes `papers.screening_status`: only the window does, in `Cmd::ScreenDecide`, `Cmd::ConfirmApply` (the ticked suggestions written together, `Store::set_screenings`: one transaction, all or none) and the detail panel. An excerpt is kept only when `ai::locate_quote` finds it in the abstract or the full text.
- The person's side of screening is `screening.rs`: `DECISIONS` and `status_of` (the keys: Y / R / U / N or 1 to 4, P or 0 for waiting again), `reason_for` (the reason kept with a decision: the assistant's when the person agrees, their own when the decision stays, none otherwise), `Round` (逐篇: the papers fixed when the round starts, the one on show, the decisions made so that the last can be taken back with what the paper was, `Before`) and `Confirming` (确认: the status chosen where it is not the suggested one, the papers left out, `plan` is what gets written).
- 提取 (`extract.rs`): a model's proposals for the custom fields. `FieldDef::hint` (a column added by `add_columns`) is what a field is said to be for, which the model is told; `extract::SUMMARY` (要点) is an ordinary Text field the window offers to add. `extract::prompt` asks about several fields of one paper in one request (the paper as `ai::paper_to_read` gives it, shared with screening) and `parse` reads the reply by field number or name; `coerce` brings an answer into the field's shape (a Select answer becomes one of its options or stays as said, which `fits` then refuses: a new option is never written) and the excerpt is kept only when `ai::locate_quote` finds it. One proposal per paper and field is kept in `field_proposals` (made beside the library's own tables, no version bump) with the definition it was asked under (`asked_as`); where it stands is read off the paper, not stored (`standing`: open, held by the field, silent, dismissed, stale), so a written value keeps the sentence behind it and taking a writing back makes its proposals wait again. `wanted` is which fields a run asks about for a paper (empty ones not asked about under the present definition; again when only the abstract was read and the full text is stored now). The person's side is `Reviewing` (ticked by rule: a value the field can hold, for an empty field, with a sentence behind it) and `taken` (a multi-value field keeps what it has). Only `Store::set_fields` writes `paper_fields` for this, one transaction, all or none; the tool `suggest_field` (in `WRITING`, not `CONFIRMING`) saves a proposal and refuses a Select value that is not an option.
- Models per task: `Settings::profiles` holds any number of model services, each with an `id` (given by `Settings::tidy` / `add_profile`, never reused while in use) and its own `effort` (`ai::EFFORTS`: empty sends nothing, `off`, or a level). `Settings::tasks` binds `Task::Chat`, `Screen`, `Translate` and `Structure` (写作's groundwork) to a profile id; `Settings::profile_for` falls back to the chat profile, then the first. `ai::apply_effort` is the one place that knows how each protocol, model and service spells thinking; a new service's way of turning it off goes there.
- Translation: `ai::translate_request` (instructions from `Settings::translation_prompt`, else `ai::TRANSLATION_PROMPT`), kept in the library's `translations` table under `store::translation_key` (text and instructions), so a text is requested once. The window translates the selected paper's title and abstract while `Library::show_translation` is on.
- Batch translation: the marked papers' menu has separate title and abstract actions. `translation::Batch` snapshots and groups the selected texts, counts progress in papers, and skips empty fields; `src/translate.rs` shares cache and in-flight requests with the detail panel and sends one batch request at a time. Stop keeps the current answer; retry reuses successes. A per-open-library `Arc` rejects late answers after closing/reopening. Debug steps `key:ctrl-a,translate:titles` / `translate:abstracts` exercise the marked selection; `translate:stop` stops it.
- Proxies: `Settings::proxy` is global and applied with `wisp_net::set_proxy` (app start, 设置 › 网络, and `wisp`); `Profile::proxy` overrides it for one model service (`direct` = none) and travels in `HttpRequest::proxy`. Empty everywhere means ureq reads the environment. `settings::proxy_problem` is the address check.
- `ToolDef::writes` marks the tools that change a library (the `WRITING` list); `wisp mcp --read-only` leaves them out, and the chat reloads the library after one ran. `ToolDef::confirm` (the `CONFIRMING` list: the imports, `run_search`, `undo_import`, `remove_search`, `find_pdf`, `organise_papers`) marks those the window's assistant runs only after the person agreed. The screening decision stays the person's: an agent may propose, never set `screening`.
- Organising (`organise.rs`, tool `organise_papers`): tags added or removed, the star, the reading status and a paragraph added to the notes (marked as the assistant's, never replacing what is there), for any number of papers in one call, written in one transaction (`Store::organise`) or not at all. `organise::apply` changes a paper in memory and says in words what it changed, and nothing where the paper already is as asked; `Store::organise_plan` is the same without writing, which `organise::preview` (`tools::preview_call`) turns into a line per paper for the consent card (`PreparedCall::details`). A call that could not run (a paper not there or in the trash) is not asked about: it fails by itself. `ai::resolve_labels` reads labels in a list of objects too, so `changes[].id` may be `P3`. A new thing an agent may change about held papers goes there; screening and the custom fields stay with their proposing tools.
- The manuscripts are read by `list_manuscripts` and `read_manuscript` (read-only). An answer goes into one by the person's hand: 插入到稿件 under an answer of the library's conversation (`MenuKind::InsertInto`, the sections of the manuscript on the writing page; `Workspace::insert_into_section`) adds it, or what is selected in it, at the end of a section with `Store::append_to_section`, which keeps the section's text as a snapshot first and the citation keys with their papers; `cite::convert_ai_citations` makes the citations the manuscript's.
- Conversations are kept per library: `conversations` holds an `ai::Transcript` (what was said, and the sources its answers cite) as JSON, `conversation_images` the pictures. What the model read is not kept: a conversation reopened from the history builds its context anew, and `ai::build_context` takes the transcript's sources as `known` so the labels in old answers still name the same papers.
- Full text for writing (`pdftext.rs`, `structure.rs`): `fulltext::file_pages` reads a PDF with hayro's interpreter first (`pdftext::pages`: glyphs with position, size and weight become lines, and a blank line marks every break the page shows, so a heading stands alone; raised citation numbers are left out, ligatures spelled out) and falls back to pdf-extract, which panics on about a third of publisher PDFs. `structure::blocks` turns the page text into paragraphs and headings, `assign_sure` gives each paragraph its part by rule (a heading that names a part, `canonical`; without an "Introduction" the text before the paper's first own heading is the introduction; a review's own headings are `other`; an "Abstract" heading lasts `ABSTRACT_WIDTH` or until a heading of the paper's own, then the part it interrupted goes on) and says where it only guessed, `sentences` cuts the kept paragraphs. A hyphen at a line's end is kept or dropped by the paper's own spelling (`Lexicon::keeps_hyphen`: the compound written elsewhere, the word written whole elsewhere, a gene or a number before it, a closed prefix, and in English two words the paper writes on their own); test a change on real lines both ways. `Store::save_fulltext_pages` does this for every text it keeps: `sentences` rows plus one `structures` row per file (`rules`, `model`, or `none` for a file without text; `open` counts the guessed paragraphs, `paragraphs` all of them, and `StructureInfo::worth_asking` / `structure::worth_asking` is the one place that decides whether a model's look is offered: many guessed, or a good share of a short piece).
- Languages: lengths are counted in `structure::width` (a Chinese, Japanese or Korean letter counts three), sentences end at `。！？．` as well, a sentence or heading may open with a letter of a script without capitals, `canonical` knows the headings of Chinese, Japanese, Korean, German, French, Spanish, Portuguese and Italian papers, and `words` gives character pairs for CJK runs (Latin words keep the stemmer; `OTHER_STOP_WORDS` beside the English ones). Each text's language (`structure::language`, from the script and the commonest words of its kept body text, `body_language`) is the `structures.language` column, `StructureInfo::language`, and `Sentence::language` on every sentence `section_sentences` returns: that is the field to read when choosing sentences by language. The writing page's groundwork line counts the texts per language when there is more than one. In `pdftext`, a page's usual line spacing (`usual_leading`) keeps Chinese set with wide leading in paragraphs, and a numbered title set like the text (`numbered_title`) stands alone. A file without a `structures` row has not been through it: `tools::extract_missing` and `Workspace::extract_missing` read such files again, so libraries from before 写作 catch up on their own; bump `structure::VERSION` when the rules change and `restructure_outdated` redoes the rule-made ones. The abstract is never taken from the PDF: `find_sentences` reads it off the record.
- Candidates: the tool `find_sentences` (part; `query` and/or `queries`; optional paper, `tag`, `starred`; `context` adds the sentence before and after from the same paper and part) ranks the sentences of one part (`retrieval.rs`): each query on its own with BM25 over `structure::words`, against a `retrieval::Index` that `index_for` keeps in memory by a hash of the part's texts (no stored word bags, so a change to `words` needs no migration), the lists merged by reciprocal rank fusion (`fuse`, then at most `PER_PAPER` per paper); without a query it returns how each paper opens the part. `tools::extract_missing` first asks `Store::structure_wanted` and returns at once when every file is sorted. The window and `/write` both go through it; `cargo run --release -p wisp_core --example retrieval_bench` times a search over 4000 made-up sentences.
- Open full texts (`openaccess.rs`, tool `find_pdf`): candidates for a paper come from its arXiv number, from OpenAlex and Europe PMC (asked by DOI or PMID, no key and no address of the asker), and, only when one of the two says the paper is open access, from the publisher's own address for the few publishers that hand a PDF to a plain client (`publisher_candidate`). Nothing logs in or goes round a wall; Europe PMC's own PDF rendering is left out because it answers browsers only. What comes back is kept only if it is a PDF (`is_pdf`), with its origin in `file_origins`. The tools take a second function for this, `sources::Download`, beside `Fetch`. In the window it is a run like the import's (`Library::fetching`, `fetch_start` / `fetch_next`).
- Completing by title (`complete.rs`, tool `find_metadata`, 按题目补全 in the detail panel for a paper with neither DOI nor PMID): `complete::find` asks Crossref, Europe PMC and arXiv for records by title (`PER_SOURCE` each), reports each source on its own (`Asked`: found, nothing, or why it failed), makes records of one DOI one `Candidate` and orders them by `similarity` (words in the same order; 1 only for the same title). The title asked for is the paper's, or, while that is the name of its file (`placeholder_title`), the one its first page shows (`pdftext::title_guess`), for the person to correct. Nothing is written by the tool or by a model: the window (`Modal::Complete`, `complete_find` / `complete_apply`) has the person pick a record and its fields; `complete::suggested` is what is ticked beforehand (blank fields, a title that is a file name) and only for a record at least `ALIKE_ENOUGH` like the title; a record the library holds as another paper is refused. There is no browser bridge and none is wanted: sources are asked over HTTP like every other lookup.
- Quotations are checked: `ai::check_quote` looks a quotation up in the stored page text (`Quoted`: found, elsewhere, only its beginning, missing, no text), `Library::check_quotes` does it for the finished answers of a conversation, the chips say the result. `ai::citation_spans` is where an answer cites, for the clickable citations in the text.
- `sources.rs` searches PubMed, Europe PMC, Crossref and arXiv (PubMed and arXiv answer in XML, read by the small `elements` helper). A saved search is a `searches` row; each run is an `import_batches` row with its papers in `batch_papers`, which is what `undo_batch` removes (untouched papers only).

### `crates/cli` (`wisp_cli`): the `wisp` binary

A thin shell over `tools` and `mcp`: argument words in, JSON out; `wisp mcp` is newline-delimited JSON-RPC on stdin/stdout. It is a separate binary because the app is a Windows GUI-subsystem program with no console. It opens the same data folder as the app (`settings::default_root` / `settings_file`), possibly while the app is running.

### Root crate (`wisp_paper`): the GPUI app

- `src/app.rs` holds all state in one root view, `Workspace` (`lib: Option<Library>` is the open library, `None` is the home page). Every click is a `Cmd` enum value, wired with `self.on(Cmd::…, cx)` and handled in `Workspace::run`. Popup menus are built from a `MenuKind` in `open_menu`; dialogs are `Modal` variants, built and submitted in `app.rs`.
- `home.rs`, `library.rs`, `detail.rs`, `chat.rs`, `dialogs.rs` are `impl Workspace` blocks that only render. A new feature usually means: a `Cmd` variant, its arm in `run`, and the element that emits it.
- Store writes go through `Workspace::change`, which runs the closure, calls `Library::reload` (re-reads papers, fields, files, trash and refilters) and shows a toast on failure. `Library::shown` is indices into `papers`, recomputed by `refilter`.
- Background work (PDF text extraction, lookups, chat streaming) runs on `cx.background_executor()` and comes back through `this.update`. Each task captures the library id (chats also a `generation` counter) and stops when the user has since closed the library or started a new conversation; keep that check in new async code.
- A library question's scope is the currently shown list (`lib.shown`), so view, search and filters change what the model reads up front. The context is built once with the first question of a conversation. `Workspace::save_chat` keeps the conversation in the library after the question and after the answer; 历史 lists them (`Chat::history`) and `open_chat` takes one up again.
- The chat is an agent loop (`ask` → `chat_step` → `run_tools` → `execute_tools` → `chat_step` …, at most `MAX_CHAT_STEPS` requests per question; before the last one the results carry `ai::LAST_STEP_NOTE`, telling the model to answer with what it has). `Chat::wire` is the conversation in the protocol's own messages and is append-only: the model's turns go back exactly as received (`ai::TurnReader` keeps thinking blocks and their signatures), and every tool call gets a result even when it did not run: refused by the person (`Chat::pending`, `Cmd::AnswerTools`), or stopped (`stop_chat`, which also keeps the text so far as the model's turn). Tools run on the background executor, each call with its own `Store` connection: a turn that only reads runs its calls side by side, one that writes runs them in order. `wisp_net::stream_chat` sends a request again, up to twice, when the service is busy (408, 409, 429, 5xx) or unreachable. Papers are named to the model by label (`P3`): `ai::resolve_labels` on the way in, `ai::add_labels` on the way out.
- A question may carry pictures (`ChatItem::User::images`, pasted into the box or picked): `picture::prepare` makes each one a model takes (PNG, JPEG, GIF, WebP; scaled down when large), `ai::user_message_with` writes them the way each protocol wants.
- 写作 (`src/write.rs` renders the editor and the candidates; `src/manuscripts.rs` the manuscripts; state in `Writing`): a library holds any number of manuscripts (`wisp_core::manuscript`: tables `manuscripts`, `manuscript_sections`, `section_snapshots`, with the `Store` methods in that file). A manuscript has a title, a language (`Writing::language`, a code of `manuscript::LANGUAGES`, default `en`) and ordered sections; a section has the person's name and a `kind`, a key of `structure::SECTIONS`, which is the part the candidates come from (`Writing::kind`; `other` for a review's own sections). A new one starts with IMRaD named in its language (`manuscript::imrad`). A section's text is saved as it is typed (`Workspace::write_typed`); a snapshot is kept `PAUSE_SECS` after the last key and on leaving the section (`write_snapshot`), only when `manuscript::worth_keeping`, at most `KEEP_SNAPSHOTS`; restoring one (`Store::restore_snapshot`) first keeps the current text. A removed manuscript is only marked (`removed_at`); a removed section goes with its snapshots, after a confirmation when it has text. Export (`manuscript::markdown`, `plain_text` for 复制全文, `docx`, a hand-written zip with stored entries) leaves out empty sections. The `drafts` table of earlier builds is emptied into one manuscript (`早先的草稿`) by `manuscript::migrate_drafts` on every open, so what an older build writes there comes in as another one; the schema version stays, since an older build reads the rest as before. Candidates are asked for, not looked up while typing (`src/write_find.rs`, `CandidateSearch`): the shortcut `write-find` (⌘↩ / Ctrl+Enter) or the panel's button searches for the selection, else the paragraph at the caret (`retrieval::paragraph_at`); the find box searches on Enter, its words as typed when they are plain Latin. Only the list of how each paper opens the part comes by itself (`write_openers`, when a part is opened), and texts read or sorted anew refresh only that list (`write_texts_changed`). What is written, in any language, is made by the translation model into three to five groups of search words in the sentences' language (`retrieval::queries_system` / `parse_groups`: content, rhetorical move, other wordings; cached per language and text in `CandidateSearch::made`), shown under the find box; without a model the words go as written and the panel says so. The part and the sentences' language are read through `Writing::kind` and `Library::sentences_language`. The `other` part is offered when some text has sentences there; the candidates can be narrowed to a tag or the starred papers, and a card unfolds into its neighbours. The model's part in the groundwork is a run like the screening one (`write_run_start` / `write_run_next`, `Task::Structure`): sorting asks about a text's outline (`structure::outline_prompt` / `parse_outline`) only for files whose rules left `OPEN_ENOUGH` paragraphs guessed, and `structure::merge` keeps the rules' labels where they were sure; reading sends each page of a file without text as a picture (`pdf::page_pictures`, `ai::read_page_request`), at most `READ_PAGES` per run, and keeps the text with `Store::save_read_pages`, which records who read it in `structures.text_by` and how many of how many pages in `pages_read` / `page_count`: a file read in part (`StructureInfo::read_in_part`) says so in the run's result and the detail panel, and the next run goes on from the first page not read. The model's help with the paragraph being written is `src/write_assist.rs` (`Writing::assist`): under the manuscript, actions on the selection or the caret's paragraph (`ai::paragraph_at`): 参照候选句改写 (the candidates on show go along with their paper and page), 译成稿件语言, 润色, and the person's own commands; `ai::Assist`, `ai::assist_prompt` / `assist_request`, `Task::Chat`'s model, streamed with `wisp_net::stream_chat`. The result streams into a card over the candidates, beside the original with the changed words marked (`ai::word_diff`; none for a translation or an own command); only the person replaces the paragraph (found again by its text, one step for `TextInput`'s Undo), inserts it below, copies or drops it. 配引用 (`ai::Assist::Cite`) adds citations and nothing else: the tool `find_citations` looks through the whole library for each sentence off the main thread, `ai::cite_candidates` names what it found by citation key, `ai::cite_request` has the model choose among those and place `[@Key]` or `[@Key, p. 5]`; the keys the result cites are kept with their papers when the person uses it (`Card::keys`). One request at a time; a new part (`Assisting::leave`), library or request drops what is in flight. The manuscript's language is `Workspace::manuscript_language`, English until the manuscript carries one.
- Citations in 写作 (`wisp_core::cite`, window side `src/cite.rs`, state `Library::citing`): written in Pandoc's form `[@Zhang2024]` (`[@A; @B]`, with locators), so a draft and its exported Markdown stay plain text and Pandoc formats them with the BibTeX of the cited papers (`cite::bibtex`, same keys, through `export::bibtex_keyed`). A key is first author + year (`DeNovo2020` from the title without authors, `-nd` without a year), a letter for the second paper with the same key; `cite::Index` gives them in the order papers were added, so a new paper never takes an earlier one's key, and a key once cited is kept in `cite_keys` (`Store::keep_cite_key`) so it stays with its paper when the record changes or another is deleted. `cite::find` resolves every citation of a text (`Found`: paper, trashed, removed, unknown, or ambiguous for the old `(Zhang et al., 2021)` form, which is still read and `cite::upgrades` rewrites into keys); `cite::references` is the list in author-year order, `reference_list` / `reference_markdown` its text. Functions take text, one section or several, never the drafts table. 引用 (`Cmd::WriteCite`, a paper id) inserts the key; under the editor the reference list of the part or the whole manuscript leads to each paper, points out what does not resolve, and offers any paper of the library by typing part of it (`Index::matching`).
- 综述 (`wisp_core::review`, window side in `src/chat.rs`): `/review` gives the conversation with the library a record (`review_projects`, one JSON body with a `revision`; `review_conversations` ties it to its conversation, and it goes with it: `Store::remove_conversation`, and the schema batch clears one left behind). `Review::step` is where it stands (1 the requirements, 2 the outline, 3 writing); `ReviewAction` is every change, applied by `Store::apply_review` against the revision the caller read. Only the person advances it: the requirements and the outline are each recorded (an answer, or what is selected in one: `Cmd::Review(ReviewDo, text)`) and then confirmed, and no section is kept before the outline is. A section kept (`ReviewDo::Section`, `section_of`) brings its evidence: `review::cited_evidence` makes a row of every citation (the sentence the citation closes, the paper behind the label, page, quotation), added once and unjudged; `Library::load_review` reads the record into `Chat::review` and looks the quotations up with `ai::check_quote` (`Chat::review_checks`) whenever the conversation, the record or the papers change, so drawing asks the store nothing. Whether a source bears a claim out is the person's (`EvidenceJudgment`, `Cmd::JudgeReviewEvidence`); a judgment keeps `Store::evidence_fingerprint` (title, abstract, the text of the page named) and stands while that and the claim's sentence do (`Review::linked`, `source_current`). There are no triggers and no version bump for any of this: `store::UNRELEASED_VERSION` is what builds between 0.5.0 and the next release wrote, and the schema batch drops what they left. The record is shown in place of the conversation (`Chat::review_open`, `render_review_record`), each text of it changed in `Modal::ReviewText`, a row in `Modal::ReviewEvidence`. A question of such a conversation carries `chat::review_note` (the step, the requirements, the outline, the sections by name), never the sections' text. `review_to_manuscript` makes a new manuscript of the sections; `cite::convert_ai_citations` turns `[P3 p.5 "…"]` into `[@Key, p. 5]`, leaving the quotation in the record.
- 图片库 (`src/figures.rs`, state `Library::gallery`, a `Gallery`): its entrance is 收藏. The sidebar's 收藏 row counts the starred papers and the figures and is lit on either page; `render_collection_switch` (文献 / 图片) stands at the top of the starred papers and of `Page::Figures`. The page is a `uniform_list` of rows of cards (`grid` decides the columns), searched by `Gallery::search` and narrowed to one of the figures' own tags (`Cmd::FigureTag`). A card's picture is read and scaled down off the main thread when its row is first drawn (`figure_thumb`: `THUMB_WORKERS` at a time, `KEEP_THUMBS` kept, the rest dropped with `cx.drop_image`). In the PDF viewer a piece cut out has 收藏到图片库 beside 用这张截图提问 (`PdfView::collect_cut` → `PdfEvent::Figure`, a `Piece` with the caption read off the page); the piece stays marked until the figure is kept (`cut_kept`), and cutting stays on for the next one. `Modal::Figure` (a `FigureForm`) is both that dialog and the one a card opens: the picture at the left (`Gallery::large`, let go of by `tend_figure_dialog` once no figure's dialog is open, however it was closed), 图号 / 图注 / 标签 / 备注 at the right. It is opened from an event without a window, so its fields do not submit on Enter and the first frame gives one the keyboard. The sparkles by 图注, 标签 and 备注 (`Cmd::FigureInfer`, no words on them by the person's wish: a tooltip says what each does) send the picture to `Task::Chat`'s model with `ai::picture_request`; the answer goes into the field with `replace_range` (one step to undo: the number only into an empty field, tags added to those there, a reading after the notes there) and nothing is kept before 收藏 / 保存. 打开原文 (`Cmd::FigureSource`) is `GotoSource` plus `PdfView::go_to_place`; the detail panel stands beside the figures as beside the papers.
- 提取 (`src/extract.rs`, state `Library::extract`, an `Extract`; every command is `Cmd::Extract(Do)`): `Modal::Extract` (a `Form`) picks the fields for the marked papers (`MenuKind::Papers`, also one paper's menu) or the list on show (自定义词条's 让助手填写…, the page's button) and says how many papers will be read (`Library::extract_plan`). The run mirrors the screening one (`extract_start` / `extract_next`: `Task::Screen`'s model, `Settings::screen_workers` at a time, `run` bumped by a start or stop, `GIVE_UP` failures in a row end it, a paper with nothing to read is counted and not asked about) and shows in the sidebar while under way. `Page::Extract` (its nav row is in the sidebar's lower group, with the number waiting) lists `Library::extract_rows` as a `uniform_list`, one row per paper and field; `Do::Apply` writes the ticked rows on show and `Extract::last` keeps what the fields held (or what was set aside) for `Do::Undo` until the page is left. The keys reach it through `screen_key` and `nav` (`extract_key`, `extract_nav`). In the detail panel `render_field_rows` draws each field with a bare sparkle (`Do::Ask`: that one field of that paper, whatever was said before); the answer waits under the field for 采纳 (`Do::Take`) or 忽略, and under a value that came from a proposal its sentence stays, leading to the page. The detail panel has no text field for a custom field, so nothing goes through `replace_range` here.
- 筛选 has three faces (`Screen::mode`, a `ScreenMode`; `Cmd::ScreenMode`): 批量 is the queue as a list with the assistant's run over it (`src/screen.rs`); 逐篇 is one paper at a time (`src/screen_single.rs`: a rail of the round's papers with what became of each, the paper with the assistant's suggestion and its abstract, the four decisions under it; a decision brings the next paper up, past the last one the round is summed up; `Library::round_paper` is the paper on show, which is not `Library::selected`: the detail panel opens beside it only when asked, Enter or `Cmd::ScreenBeside`, and then follows the round); 确认 is the suggestions for the waiting papers looked over and written together (`src/screen_confirm.rs`: a row per paper with the status it will get, ticked unless left out; what is on show is written by `Cmd::ConfirmApply` and can be taken back, `Screen::confirmed`). A finished run of the assistant leads to 确认; it cannot be entered while a run is under way. `Workspace::render_advice` draws a suggestion in full in all three, and `Cmd::ScreenAskOne` asks the assistant about one paper (`screen_start` with `only`). The keys are fixed bindings in the context `Workspace && !TextInput` (`shortcuts::rebuild`, listed read-only in 设置 › 快捷键 from `SCREEN_KEYS`) that end in `Workspace::screen_key`: about the round's paper, the paper open in the queue, or the row the keys are on. The arrow keys there go through `Workspace::screen_nav`, and Esc leaves a round or the confirmation for the queue. A row of a `uniform_list` needs `w_full()`, or it is as wide as its content.
- The conversation with the library is the page 助手 (`Page::Ask`; it was 向文献库提问 until what it does outgrew the name; the paper's tab is still 提问). Before anything is said it shows what the assistant can be asked to do (`render_start` in `chat.rs`): cards by kind (找文献, 读文献, 整理, 写), two to a row whose lines are either a request sent as it stands (`Cmd::Suggest`) or a slash command left in the box for its words (`Cmd::StartCommand`, its description read off `ai::SLASH`). A card has a width of its own: one that shares the row's width is measured before its lines wrap. `Task::Chat` is labelled 助手 as well, and each task's row in 设置 › AI says which features use its model; a new feature that calls a model is added to that sentence.
- Slash commands are the `ai::SLASH` table (name, description, what follows it, prompt template; an empty template is a command the window carries out, `/new`). `ai::slash_matches` is what the popup over the box offers; while it shows, `TextInput::choosing` hands Up, Down, Tab and Escape to `Workspace::chat_input`. A new command is one entry in the table. The person's own commands are `Settings::commands` (`ai::Command`: name, description, template; 设置 › 命令), read after the built-in ones by `ai::read_input`, which therefore cannot be replaced; `{}` in a template is what follows the name, and a template without it takes what follows at its end. A question keeps what was sent for it (`ChatItem::User::prompt`, `Said::User::prompt`, empty when that is the text), so replaying a conversation does not read a template again; only a question from before that is expanded anew (`ai::expand_slash`, built-in commands only).
- An answer is drawn as Markdown: `wisp_core::markdown::parse` (blocks and inline marks, rules ported from quiet.md; what does not close stays as written, since an answer is drawn while it streams) and `src/markdown.rs` (`render`). Citations like `[P3 p.5 "…"]` stay ordinary text; the chips under an answer come from `ai::citations`, the first `SOURCES_SHOWN` of them until `Chat::sources_open` holds the answer's index.
- `settings.rs` is the settings view (通用, 外观, 快捷键, AI, 网络, 关于). On the AI page the models are a list whose open row shows its fields (`ProfileFields`, made anew for the model on show). It replaces the page while `Workspace::settings_view` is `Some`; the open library stays underneath. There is no save button: each change writes `settings.json` at once.
- `shortcuts.rs` owns every key binding. `shortcuts::rebuild` clears and re-binds all of them (the text field's too) from the defaults plus `Settings::shortcuts`; call it after any change. While 设置 › 快捷键 waits for a key, all bindings are cleared and `Workspace::record_key` receives the key. A new shortcut needs an entry in `SHORTCUTS`, an action, its binding in `rebuild`, an `.on_action` in `home.rs` and an arm in `Workspace::shortcut`.
- Motion is `with_animation` through the helpers in `ui.rs` (`spinner`, `fade_in`). An animation's state lives under its element id, so give animated rows an id made from what they show (a paper id), not their position: the screening queue is sorted anew with every suggestion.
- A wrapping `TextInput` under ancestors whose widths are all percentages (the settings column) is measured at 240px; give its wrapper a pixel width there, as `ai_page` does for the translation instructions.
- Colours come only from `theme.rs`, which has a light and a dark set (`theme::dark()`); `Workspace::apply_appearance` picks one from the setting or the system. Do not hard-code colours elsewhere; text on an accent fill is `Theme::on_accent()`, a library colour is `Accent::strong()` / `soft()`.
- The release check (`check_update`) reads the redirect of GitHub's `releases/latest` (the JSON API is rate-limited per address). It only notifies and opens the release page: nothing is downloaded or installed.
- PDF import is a run (`Library::import`, an `ImportRun`): a folder dropped or picked (添加文献 › 导入文件夹…) is expanded by `import::folder_pdfs`, each folder between it and a PDF becoming a tag of that paper (merged into a paper already held); `import_paths` reads `IMPORT_WORKERS` files side by side, `add_pdf` adds a row for each, the sidebar shows the progress and then the summary until it is put away, `Modal::ImportReport` the rows. One file alone is a toast instead.
- The keyboard and the right button (`src/context.rs`): the arrow keys, Page Up/Down, Home/End, Enter and Delete are fixed bindings in the `Workspace` context (`shortcuts::rebuild`) that end in `Workspace::nav`: in an open menu they move along its items, else they move in the papers on show (全部文献 and 筛选; left and right turn the pages of a PDF on show, else move a screenful), Enter opens the PDF, Delete or ⌘⌫ moves the paper to the trash and the one that takes its row is selected. A text field with the keyboard hears them first; a one-line or empty field passes Up and Down on. A right click is `.on_mouse_down(MouseButton::Right, self.on_context(MenuKind::…, cx))`, its items in `context_menu` (`Menu::breaks` are the lines between groups, `Menu::paper` the row marked meanwhile): papers, trashed papers, files, tags (rename and remove: `Workspace::retag`), past conversations, answers.
- Several papers at once (`Library::marked`, 全部文献 only): a click with ⌘ / Ctrl adds or takes one (`Workspace::mark`), with Shift the stretch from `Library::anchor`; Shift with an arrow moves `Library::cursor`, ⌘A marks the list on show, Esc lets go. More than one marked puts the detail panel away, and showing one paper (`select`) ends the marking. A right click on a marked row is `MenuKind::Papers`; its commands end in `Workspace::run_batch` (`AskPapers`, `StarPapers`, `ReadPapers`, `TagPapers`, `FindPdfsOf`, `AskTrashPapers` / `TrashPapers`). `AskPapers` starts a new conversation with the library about those papers alone: `Library::asked`, read through `Library::scope_papers` wherever the scope of a library question is shown or built, and emptied by the next new conversation.

While the button is held a layer over the window follows the pointer, as for the edges. Use it for any text a reader may want to copy.

An element only hears the pointer moving over itself, so while an edge is held (`Workspace::resizing`, an `Edge`) a layer over the whole window takes the moves (`home.rs`); do the same for any other drag. A tap is over before that layer is drawn, so each edge also hears its own mouse-up.
- The library's sidebar is `Settings::sidebar_width` (0 is `SIDEBAR_W`) and `Settings::sidebar_hidden`: its right edge is dragged (`Workspace::drag_sidebar`; pulled in past half of `SIDEBAR_MIN` it is put away, back out and it returns), clicked twice it is put away, and `Cmd::ToggleSidebar` (the button at the top left, the shortcut `sidebar`) puts it away or brings it back. Widths are computed from `Workspace::sidebar_width`, never from the constant. The two top-left buttons (`render_corner`) are drawn in the sidebar or, while it is away, over the list at the same place, level with macOS's traffic lights.
- Reading mode (`Library::reading`, `Cmd::ToggleReading`: the button on the PDF's toolbar, the shortcut `reading`, Esc to leave before Esc closes the paper): `detail_width` is then the window's and `render_library` draws the detail panel alone, with a one-line header and no left edge. Nothing is made anew, so `Library::pdf` keeps its place and `paper_chat` its conversation and unsent text; leaving the paper, changing the page or the search shortcut ends it. The conversation's width beside the PDF is `Settings::chat_width` (0 is a share of the panel; `Workspace::chat_width`, `split_chat_width` in `library.rs`), dragged by the edge between the two (`Edge::Split`, `drag_split`).

The wheel is heard in the capture phase by a canvas under the list (`PdfView::wheel`), since the list would scroll before a parent could zoom.

A paper without a PDF keeps the layout, with 添加 PDF / 查找开放全文 at the right, so the arrow keys do not change the layout from paper to paper. A citation followed from that conversation, a passage or a picture sent from the PDF, all end there.

The title bar moves it, the bottom-right corner sizes it (`MIN_WIDTH` / `MIN_HEIGHT`), 分栏 goes back beside, the minus folds it into a round button that a drag moves and a click opens (`is_drag`: farther than `DRAG_SLOP`). Place, size and folding are saved; `fit` keeps what is drawn inside the area, which is measured as it is drawn (`Library::float_area`), and leaves the stored place alone, so a window grown back finds it. A held title bar, corner or button is `Library::float_drag`, heard by a layer over the whole window (`render_float_layer`, drawn in home.rs) like the edges. The window and button `occlude()`, so the PDF under them hears neither wheel nor press while the rest of it scrolls and selects as before. A passage or picture sent from the PDF opens a folded conversation (`unfold_chat` in `show_paper_chat`). The switch to floating is 悬浮 in the conversation's header (`render_float_switch`).
- Selecting in a PDF: the worker hands out a page's glyphs (`pdftext::page_marks`, after the page is drawn), `PdfView` keeps a `Selection` of them on one page (`mark_at`, `mark_boxes`, `marks_text` in core), and tells its owner through `PdfEvent` (copied; a passage for a conversation, kept in `Chat::quotes` and written into the question as `[P3 p.5 "…"]` by `ai::quoted_passage`; a piece of a page cut out as a picture; a passage to translate). 翻译 puts a card by the selection (`card_place` keeps it in view): `Workspace::translate_passage` goes through `translate_text` (`src/translate.rs`), the same path and cache as the title and abstract and the batch, and `sync_pdf_translation` hands the state back (`PdfView::show_translation`). Its menu asks one of `Settings::profiles` for this once, without changing the settings, and that answer replaces the kept one (`Store::replace_translation`; the cache key has no model in it); `Library::translation_asks` drops an answer that a later request for the same text overtook.
- Selecting in an answer: `markdown::render` takes a `Selecting`, keeps the `TextLayout` of every piece it draws and reports where the pointer is as a `Place` (piece, byte); the selection is `Chat::picked`, its text `markdown::text_between`.
- A window that is not on screen draws no frames: in a scripted run, pointer steps need a `shot:` before them, or there are no hitboxes to hit.
- `input.rs` is the app's own text input (single / multi-line, IME via `EntityInputHandler`; a field that `accepts_images` hands pasted pictures to its owner; Cmd/Ctrl+Z and Shift+Z undo and redo, letters typed in a row being one step; `replace_range` is an owner's change as one step); `pdf.rs` renders pages with `hayro` on a worker thread into a virtualised list, keeping a bounded number of pages.
- `build.rs` embeds every file under `assets/` (of `branding/`, only `app-icon.png`) into the binary; icons are loaded by name through `ui::icon`. On Windows it also compiles the icon resource.

### `site/`: the project page

https://xuzhougeng.github.io/WispPaper/ is three hand-written files (`index.html`, `style.css`, `site.js`), no generator and nothing loaded from another host (no web fonts: the stacks are system ones). `site/build.sh [folder]` adds the screenshots from `docs/images` and the icon; `python3 -m http.server --directory dist/site` shows the result. `.github/workflows/pages.yml` deploys it on a push to main that touches it and after every published release, writing `release.json` (the latest release's files) next to the page: the download buttons read it, and lead to the release page without it. The page is laid out as a paper (numbered figures, citations that can be clicked); its numbers are those of `docs/TUTORIAL.md`, and its colours are `theme.rs`'s. Keep it out of `scripts/`, whose changes rehearse the packaging.

### `vendor/`

`gpui` 0.2.2, `taffy` 0.9.0 and `xattr` 0.2.3 are vendored with local patches and wired in through `[patch.crates-io]`. Patched spots carry a `quiet.md:` comment and are listed in `vendor/PATCHES.md`. When changing vendored code, add a row there and keep the comment; do not bump these versions without re-applying the patches. GPUI APIs here are 0.2.2 plus those patches (for example `grid_col_widths`, `ListState::estimated_scroll_metrics`), so check `vendor/gpui/src` rather than upstream docs.

## Scope

Ported from BiblioCell, without its datasets and web version. Being added step by step: the tool layer with CLI and MCP (done, read-only tools), the chat as an agent loop over the tools with `/search` and `/cite` (done), search sources with trial queries and batch import (done: 检索与导入 page, `src/searches.rs`), a guide page for a new library that starts from a search (done: `src/guide.rs`; `ai::query_prompt` / `parse_queries` ask the model for queries per database, each is tried with `search_online`, the person picks), AI screening suggestions that the person confirms (鲸吞法: import broadly by query, let the agent judge, the person decides; done: 筛选 page in `src/screen.rs`, with 逐篇 and 确认 beside it, `screening_suggestions` table, `ai::screen_prompt` / `parse_judgement`, tool `suggest_screening`), scheduled source sync (done: `LibraryInfo::auto_sync_hours`, tool `sync_searches` with `tools::due_searches`, `Workspace::watch_searches` looks once a minute), and jumping to the quoted sentence in the PDF (done: the assistant may cite `[P3 p.5 "a sentence"]`, parsed by `ai::citations`; `PdfView::find` has the worker interpret the page with a glyph-collecting hayro `Device`, and `fulltext::find_quote` / `line_boxes` turn the match into one box per line, drawn over the page image). That roadmap is complete; what each step left out is in its pull request (2 to 8). After it: 写作, a writing page whose advantage is candidate sentences from the same part of the library's papers, on top of PDFs read with their layout and sorted into parts (rules first, a model where no heading says, a model's eyes for scans). Then 图片库, after CiteBox's figure library: figures and tables cut out of the PDFs and kept with their legend, tags and notes, entered from 收藏. API keys are stored in plain text in `settings.json`; when empty, `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` are read from the environment.
