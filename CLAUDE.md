# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Wisp Paper is a local-first literature library desktop app (collect papers, organise, preview PDFs, ask an LLM about the library), written in Rust with GPUI. Targets Windows and macOS; Linux compiles but is untested. The desktop UI supports Chinese and English (Settings › General). Use `i18n::t` with Chinese keys in `locales/en.json` for static labels, and `tf!` with both Rust format literals for dynamic messages. Translate shared label tables at display sites; keep stored keys, user content and model prompts unchanged. Code comments are in English.

## Commands

```sh
cargo run --release                     # run the app
cargo test                              # all four crates (workspace default-members)
cargo run -p wisp_cli -- help           # the `wisp` command line; `-- mcp` is the MCP server
cargo test -p wisp_core                 # engine only; no GPUI build, much faster
cargo test -p wisp_core store::         # one module's tests
cargo test -p wisp_core <test_name>     # one test
cargo test -- --ignored lookup          # live Crossref / Europe PMC lookups (network)
cargo clippy --all-targets              # expected to be warning-free
```

- The toolchain is pinned in `rust-toolchain.toml` (clippy only). There is no rustfmt component and no `rustfmt.toml`: the code is hand-formatted with long lines and one-line `if x { return }` bodies. Do not run `cargo fmt`; match the surrounding style.
- Windows needs the MSVC build tools.
- CI (`.github/workflows/ci.yml`) runs clippy with `-D warnings` and the tests on Windows and macOS, and the three windowless crates on Linux. A release is a pushed tag `v<version>` that matches the version in `Cargo.toml` (`release.yml`; notes from `.github/release-notes/v<version>.md`). It is always signed, the way BiblioCell does it: `scripts/package-macos.sh --arch universal` builds, signs with the Developer ID certificate, notarizes and staples the app and the DMG; `scripts/package-windows.ps1 -Sign` signs both exes through SSL.com eSigner (`scripts/sign-windows-esigner.ps1`); Linux is an unsigned tar.gz. The ten secrets are listed at the top of `release.yml`; with one missing the run stops before building. A pull request touching `scripts/` or the workflow rehearses the packaging unsigned. Locally `CARGO="cargo +stable" scripts/package-macos.sh` gives an ad hoc signed `dist/Wisp Paper.app`.
- Demo data: `cargo run -p wisp_core --example seed -- /tmp/wisp-demo some.pdf`, then `WISP_PAPER_HOME=/tmp/wisp-demo cargo run`. Further PDFs after the first become papers of the second library with their full text, which is what 写作 needs.
- A PDF that comes out wrong: `cargo run -p wisp_core --example structure -- a.pdf [blocks|sentences|pages|outline|captions|apply reply.txt]` prints what the reader and the structuring make of it (its language, how many paragraphs the rules guessed and whether a model is worth asking, sentences per part; every block with its label; every sentence kept; the page text; the outline a model is asked about; the captions of figures and tables each page shows, as the figure library reads them; the parts a model's answer gives).

## Architecture

A Cargo workspace of four crates. Dependencies point one way only: `wisp_net` depends on core, the app and the command line depend on both.

### `crates/core` (`wisp_core`): the engine, no GPUI

Everything that can be decided without a window or a socket lives here, and it is where nearly all tests are. That includes the pure halves of networked features: `lookup` builds Crossref / Europe PMC URLs and turns their JSON into a `Paper`; `ai` builds the context, the request body for the three protocols (Anthropic Messages, OpenAI-compatible chat completions, OpenAI Responses) and parses stream lines into `StreamEvent`s. The actual HTTP (blocking `ureq`) is in `crates/net` (`wisp_net`), shared by the app and `wisp`; its tests serve canned responses from a local port. Code in core that needs the network takes the fetching function as an argument (`sources::Fetch`), so core tests pass a closure.

Author names are kept as the source wrote them, `A; B; C`, in three forms: `Zhang, Tian-Qi` (PubMed, Crossref, BibTeX), `Tian-Qi Zhang` (arXiv, Zotero) and, in libraries from before, `Zhang TQ` (Europe PMC, the family name first and initials after it). `model::author_names` is the one reader that says which word is the family name, for a whole list at once (a name ending in one capital is the third form, one ending in two or three when most of the list is written so); `Paper::citation`, the citation keys and reference list of `cite`, and the BibTeX of `export` all go through it, and a new reader of names does too. `lookup::europepmc_hit` now stores such names with their comma (`model::family_first`, or the name's own parts when the record has them). A key already cited stays as `cite_keys` has it.

On-disk layout: the data root holds one folder per library, each with `library.json` (`libraries`), `wisp-paper.sqlite` and `papers/` (`store`). Attachment paths in the database are relative to the library folder so a folder can be copied elsewhere. Removing a library or attachment moves it to `removed/`; nothing is deleted.

`store.rs` notes:
- The schema is one `CREATE TABLE IF NOT EXISTS` batch guarded by `SCHEMA_VERSION` / `PRAGMA user_version`; a newer database is refused. Bump the version when an older build would misread the data.
- Deduplication is by DOI, PMID (`paper_identifiers`), then `title_key`. Trashed papers stay in `papers` (marked by a `trashed_papers` row) so they keep blocking re-import.
- `Store::in_memory` is what tests use.
- `Paper::fulltext` is computed, not stored: `missing`, `linked`, `stored`, or `textless` (a full-text file is there and no text came of any). Why a file gave no text is the sentence kept in `fulltext_text.error`; `fulltext::failure_kind` tells the kinds apart (`locked`, `parser`, `encoding`, `no_text`, `file`, `unsupported`), messages of earlier builds included, and a new reason is a constant there, not a string somewhere else.
- Status values are stored as English keys and shown through the label tables in `model.rs` (`SCREENINGS`, `READINGS`, …). The labels are not translations: the stored key `excluded` is displayed as 「相关」.

`docx.rs` reads and writes Word files for 写作, by hand (a zip reader that keeps unchanged entries as packed, an XML tokenizer that keeps what it does not change as written): a tree parser that writes its tree again would not promise an untouched paragraph back to the byte. `read` gives the body's paragraphs that say something (text of `w:t`, a tab or line break as a space; struck text not counted, inserted text counted; no table of contents, nothing inside tables), each heading's level (its style's name `heading N`, which Word keeps in English, or an outline level) and the comments with the words their ranges cover. `rewrite` takes the paragraphs the manuscript now has (`Wanted`: text, role, comments) and writes the same file saying them: `align` matches old and new paragraphs (equal ones first, then those alike by `likeness`, as many leftovers as came changed in place, the rest taken out and put in), an unchanged paragraph is the original XML, a changed one is changed inside its runs (`Para::edited`: word-level `ops`, what stays keeps its run, what comes joins the run of the text before it; `Options::track` writes `w:ins` / `w:del` with ids after the file's largest), a new one is set like the nearest paragraph of its kind, and one taken out that holds a section break or a picture keeps those. Marks with another half elsewhere (bookmarks, comment ranges, field characters) are never dropped. Comments go into `word/comments.xml` (made with its relationship and content type when the file has none) and their ranges cut the runs they start and end in. The tests build small files; real ones are tried with the `docx` example and LibreOffice.

`comment.rs` is 批注: `manuscript_comments` (made beside the library's tables, no version bump), each about a quotation of its section and found again by what it says (`locate`: as written, else by its characters without spaces and quote styles), from a Word file (`FILE`: never removed, only marked `DONE`), the person, or the assistant. `review_prompt` / `parse_review` are the assistant's review of a section: a JSON list of `{quote, comment, replacement}`, each quotation checked against the text (kept only when found within one paragraph and not overlapping an earlier one). A proposal is taken only by the person (`Comment::taken`: the comment moves to the new words and keeps the old; `taken_back`). `manuscript.rs` has the rest: `from_word` / `from_markdown` make a `Draft` (sections at the highest heading level; a Word file without heading styles has its headings guessed by `headings::guess` (a name every paper has, numbering `一、` / `（一）` / `1.1`, a figure at the end `（图1）`, bold, a short line between running text; numbered items next to each other are a list, nothing after 参考文献), listed in `Draft::headings`, and is cut only at those the person ticks in `Modal::Headings` (`from_word_with`); a Markdown file without headings at `structure::canonical` names; a title; `bare` for text under no heading), `Store::split_section` / `merge_section` are 设为标题 / 从这里拆成新节 under the editor and 并入上一节 in a section's menu: a heading made of a paragraph is written back as that paragraph, a section cut off without one is `bare` and its name goes into no file. `Store::import_manuscript` keeps it with the Word file itself under `manuscripts/` and a `manuscript_sources` row, `wanted` lays the manuscript out as the file's paragraphs with the comments on them, and `Store::manuscript_word` is the export (the source file written again, or `docx()` with comments for a manuscript that has none). `read_manuscript` lists a section's open comments.

`citefind.rs` is 配引用: the papers of the library a text can cite, sentence by sentence, and nothing that writes a word of the manuscript's. `sentences` cuts a text and keeps where each sentence stands (full stops of either script, semicolons, line breaks; not after an abbreviation, inside a number or inside brackets); `plan_prompt` / `parse_plan` are what a model says of each sentence before the search: what it does (`INTENTS`: background, a finding of someone else's, a method, an open question, a comparison, the authors' own words) and the search words for it in the library's language (`library_language`; `words_prompt` / `parse_words` are the words alone, which 出处 uses); `search` ranks the papers for every sentence, each query twice (by the record, and by the paper's best sentence among the abstract's and the stored full text's, over `retrieval::index_for`), merges the rankings and names the sentence that matches best, keeping a paper only when record and sentence hold a fair share of a query's words. What a sentence can cite goes by what it does: for a finding, a comparison or a method a sentence outside the paper's introduction is named when one fits, background puts the reviews first (`reviews`: a full text without methods or results, or a record that says so), the authors' own words are not searched for. `named` reads the works a paper's sentence names by author and year (`(Tang et al., 2009)`; numbered citations name nothing, the reader leaves raised numbers out) and `holds` finds the library's paper for one. `judge_prompt` / `parse_judgement` are a model's choice among the papers found, by a standard per intent (a JSON list of sentence, `cite` with key, role `SOURCE` or `REVIEW` and why, and `restates`: papers that only tell what others found, which are no citation but a lead to the works they name; it chooses, it never names a paper of its own); `place` / `placed` write `[@A; @B]` before the mark a sentence ends with, into a citation already there, never a key twice. The tool `find_citations` (text, optional `queries` and `intents` per sentence, `perSentence`) is `sentences` plus `search`, each candidate with `review` and the `names` of its sentence.

`passage.rs` is 出处: the sentence of a paper that a citation of the manuscript rests on, so a reference leads to where it is from and not only to the paper. `cite_passages` (made beside the library's tables, no version bump) keeps one per manuscript, paper and citing sentence (`claim`: the sentence without its citations, `passage::claim`), with the paper's sentence, its part and page, why, and where it is from (`CITED`: the person cited from that sentence; `MODEL`: looked for afterwards and chosen by a model; `WORDS`: found by words alone, unchecked). Nothing is written into the manuscript, whose text stays `[@Key]`: `citations` gives every citation its sentence and `assign` finds its passage again by how alike the claims are (`docx::likeness`), so it stays with the sentence while the text is written on; a sentence written anew or translated takes the paper's unclaimed passage of that section, said to be `loose`. Looking afterwards: `sentences_of` is what a paper says of its own (the abstract's sentences, then the stored full text's), `nearest` ranks them against the sentence and any search words (BM25, merged; `fair` when one holds a fair share of the words), `choose_prompt` / `parse_choice` are a model's choice among them, which may be none: then a row without a passage is kept (`Passage::found`), said under the reference as a citation its paper does not bear out, and not asked again. The tool `find_passages` (paperId, `texts`, optional `queries`) is `sentences_of` plus `nearest`; `read_manuscript` lists each section's passages. `Store::merge_section` / `split_section` take the passages along, and `cite::convert_ai_citations` hands back the sentences an answer quoted (`Quoted`) for `passage::quoted`.

`revise.rs` is 改稿, the engine of the box under the manuscript where the assistant is told what to change in a section. The model answers with SEARCH/REPLACE blocks (`<<<<<<< SEARCH`, the words to find, `=======`, the words to put there, `>>>>>>> REPLACE`; no words to find is the end of the section, no new words a deletion), so a change can be made the moment its block is complete. `read` reads a reply as far as it has come (the complete blocks, the one being written once its words to find are in, what is said beside them; words begun on the opening marker's line and a block not closed are read too, as smaller models write them), `find` / `place` say where a change goes in the text as it now stands (as written, nearest to the last change, else by `comment::locate`; a paragraph taken out takes its empty line along), `follow` keeps a place while one stretch of the text changes around it, `added` is the new words to light up (`ai::word_diff`), `prompt` what the model is told. No store, no tool: the window makes the changes.

`compose.rs` is 助手写, the writing page's other mode, in which the assistant leads: the person talks with it and it writes the manuscript with two tools of its own. `edit` is the tool `edit_section`: one section written or changed, by `edits` (each made where its words stand, `revise::place`; no words to find is the section's end) or by `text` (the section's whole new text); citations are `[@Key]`, or `[@<paper id>]` which `keyed` turns into the key, and the keys cited are kept with their papers; the section's text is kept as a snapshot (`assistant`) first, and what was not found is handed back as `missed`. `outline` is the tool `set_outline`: the sections a manuscript is to have, in order, with its title and language when given; a section named by id or present name stays what it is, the others are made (`Store::arrange_sections`, one transaction), and one left out goes only when nothing was ever written in it (no text, no snapshot): one with text stays, after the others, and is said (`kept`). `call` is what a conversation's tool call goes through instead of `tools::call_in`: for `edit_section` the citations of the words to be written are the conversation's (`label_citations`: `[P3 p.5 "…"]` to `[@Key, p. 5]`), the sentences they quote are kept as passages where the paper says them (`keep_quoted`, origin `CITED`), and the result names the quotations no paper holds and the labels that name no paper, for the model to put right. `note` is what every question of such a conversation tells the model: the manuscript's id, language and outline with lengths, the section on show, what is selected, and how to work (read before changing, find the sentence before citing, nothing of the manuscript's text in the conversation). `hunks` is what changed between two texts line by line, which the window lights. No table and no version bump: the conversation is an ordinary one, kept under the manuscript's id.

`figure.rs` is 图片库: pieces cut out of PDF pages and kept as pictures under `figures/` in the library folder, one `figures` row each (number, legend, notes, tags of their own, and the paper, file, page and box they came from). The table is made beside the library's own like the manuscripts'; no version bump. `caption` finds the caption a piece belongs to among the page's lines (`pdftext::lines`): a line that `opening` takes for a caption's start (`Fig. 2 |`, `Figure 3.`, `Table S1`, `Extended Data Fig. 4`, `图 3`; not running text that begins `Figure 2 shows` or `Fig. 2a). These`), the nearest within `REACH` that shares the piece's columns (a figure's under it, a table's over it), read on through the lines set alike under it. `Ask`, `ask_prompt` and `read_legend` / `read_tags` / `read_notes` are what a model that sees the picture is asked and how its answer is read. A figure is listed while its paper is outside the trash; `delete_paper` and `remove_figure` set the picture aside in `removed/`. A picture a model drew is a figure without a paper (`paper_id` empty, `Figure::drawn`): so `paper_id` is no reference to `papers`, a trigger takes a deleted paper's figures along instead, and `figure::migrate` makes over the table of a library from before (same columns, so an older build reads it as before). Tool: `list_figures` (read-only).

`tools.rs` is the one table of what an agent can do with a library; the command line, MCP and (next) the in-app assistant all end in `tools::call`, so a rule belongs there and not in a front end. `ai.rs` holds the model side of the loop: the request with tool definitions for each protocol, `TurnReader` (one streamed turn → text, tool calls, the message to send back), `tool_results`, and the slash commands (`SLASH`: the prompt templates behind `/search`, `/cite`, `/review`, `/compare` and `/write`).
- A new tool is an entry in `catalog()` (name, Chinese description, JSON Schema) and an arm in `call_in`. Nothing else: `wisp <tool>` reads its flags off the schema (`cli_args`), and `mcp::handle` lists and calls whatever the catalog holds. The test `every_tool_is_callable` fails when an entry has no arm.
- Tools take `library` (id or name, optional when there is one library) and return JSON; an error is a Chinese sentence for the caller, person or model.
- Screening is against the library's goal (`LibraryInfo::criteria`, 筛选目标; empty means by the topic), saved as it is typed. Each suggestion keeps the goal it was made against (`screening_suggestions.criteria`, NULL for one from before, which counts as current; `Suggestion::made_for`); one made for another goal is shown as 按旧目标 and asked again by the next run. 复核 (`Cmd::ScreenRecheck`) asks about the decided papers too: one the assistant now sees otherwise comes back to the queue (`Library::rechecking`, until the person decides it again, which keeps or changes the decision), the decision itself is never touched. Columns added later go through `store::add_columns`.
- A suggestion never writes `papers.screening_status`: only the window does, in `Cmd::ScreenDecide`, `Cmd::ConfirmApply` (the ticked suggestions written together, `Store::set_screenings`: one transaction, all or none) and the detail panel. An excerpt is kept only when `ai::locate_quote` finds it in the abstract or the full text.
- The person's side of screening is `screening.rs`: `DECISIONS` and `status_of` (the keys: Y / R / U / N or 1 to 4, P or 0 for waiting again), `reason_for` (the reason kept with a decision: the assistant's when the person agrees, their own when the decision stays, none otherwise), `Round` (逐篇: the papers fixed when the round starts, the one on show, the decisions made so that the last can be taken back with what the paper was, `Before`) and `Confirming` (确认: the status chosen where it is not the suggested one, the papers left out, `plan` is what gets written).
- 提取 (`extract.rs`): a model's proposals for the custom fields. `FieldDef::hint` (a column added by `add_columns`) is what a field is said to be for, which the model is told; `extract::SUMMARY` (要点) is an ordinary Text field the window offers to add. `extract::prompt` asks about several fields of one paper in one request (the paper as `ai::paper_to_read` gives it, shared with screening) and `parse` reads the reply by field number or name; `coerce` brings an answer into the field's shape (a Select answer becomes one of its options or stays as said, which `fits` then refuses: a new option is never written) and the excerpt is kept only when `ai::locate_quote` finds it. One proposal per paper and field is kept in `field_proposals` (made beside the library's own tables, no version bump) with the definition it was asked under (`asked_as`); where it stands is read off the paper, not stored (`standing`: open, held by the field, silent, dismissed, stale), so a written value keeps the sentence behind it and taking a writing back makes its proposals wait again. `wanted` is which fields a run asks about for a paper (empty ones not asked about under the present definition; again when only the abstract was read and the full text is stored now). The person's side is `Reviewing` (ticked by rule: a value the field can hold, for an empty field, with a sentence behind it) and `taken` (a multi-value field keeps what it has). Only `Store::set_fields` writes `paper_fields` for this, one transaction, all or none; the tool `suggest_field` (in `WRITING`, not `CONFIRMING`) saves a proposal and refuses a Select value that is not an option.
- Models per task: `Settings::providers` holds any number of model services (`provider::Provider`: address, key, proxy, protocol, and the `Preset` it started from), each offering any number of `provider::Model`s with an `id` (given by `Settings::tidy` / `add_provider` / `add_model`, unique across providers, never reused while in use) and its own `effort` (`ai::EFFORTS`: empty sends nothing, `off`, or a level). A new settings file starts with DeepSeek, Kimi and GLM (`provider::DEFAULT_PRESETS`); each preset has its own key variable (`DEEPSEEK_API_KEY` …), so one service's key never goes to another. What a request is made with is still the flat `ai::Profile` (`Provider::profile`, `Settings::profile` / `profiles`). `Settings::tasks` binds `Task::Chat`, `Screen`, `Translate` and `Structure` (写作's groundwork) to a model id; `Settings::profile_for` falls back to the chat model, then the first that can answer, then the first. A file from before providers keeps `profiles`, which `Settings::load` turns into providers (`migrate`: profiles with one address, key and proxy become one provider, their ids kept) and never writes again. `ai::apply_effort` is the one place that knows how each protocol, model and service spells thinking; a new service's way of turning it off goes there.
- 生图 (`imagegen.rs`): a provider's model either answers in words or draws (`provider::Model::kind`, `imagegen::KIND`; `Model::draws`). A name that says so makes a model added a drawing one (`imagegen::looks_like`, in `Settings::add_model`), the model's menu on 设置 › AI › 模型 changes it (`Settings::set_model_kind`), and presets bring theirs (`Preset::images`: OpenAI's gpt-image, the `gemini` preset, `ark` for 火山方舟's Seedream). `Task::Image` is bound only to a drawing model and the other tasks never to one (`Settings::tidy`); `Settings::profiles` lists the models that answer in words, `image_profiles` those that draw, and `profile_for(Task::Image)` is `None` while no model draws: it borrows nothing (`Task::WORDS` are the other four). A drawing model is asked through one of three interfaces (`imagegen::Interface`, chosen in `Model::interface` or guessed by `imagegen::guess`): OpenAI's Images API (`{base}/images/generations`, also Seedream and most relays), Gemini's own `generateContent` (at Google's address; from a base ending in `/openai` or `/v1` the root is worked out), or chat completions that answer with a picture (a Gemini model behind a relay). `imagegen::request` builds the request (sizes and parameters per model family go there), `imagegen::read` finds the picture in the answer (bytes, or an address to fetch), `wisp_net::generate_image` sends it and returns a PNG, JPEG or WebP. A new service's way of asking for a picture is an arm in those two functions.
- 判断 (`judge.rs`): the third kind of model (`judge::KIND`, `Model::judges`; `Model::speaks` is one that answers in words), after TypeSafe's System One models (Jev): given a state and questions whose answers are fixed beforehand, it answers each with one of them and a probability for every one, and writes nothing. The `typesafe` preset brings `jev-latest` (`Preset::judges`), a name beginning `jev` makes a model added one (`judge::looks_like`), and the model's menu says its kind (`Cmd::SetModelKind`, `Settings::set_model_kind`). `Task::takes` is the one place that says which kind of model does which task: only `Task::Screen` takes a judging model, and only when the person chose it (`profile_for` never falls back to one); 提取, which shares screening's model, asks `Settings::speaking_profile_for`. In a screening run (`screen_next`) such a model is asked with `judge::screen_request` (one `choice` question, include / related / irrelevant, about the record and abstract, or the first pages without one; `POST {base}/systemone`) through `wisp_net::judge`, and `judge::read_screening` makes the `Judgement`: the verdict with the highest probability, 证据不足 when its confidence is under `SURE_ENOUGH`, the probabilities as the reason, no excerpt. Errors come as `detail` (`ai::error_message`). A new use of such a model is a question built with `judge::request` and a reader for its answer.
- Translation: `ai::translate_request` (instructions from `Settings::translation_prompt`, else `ai::TRANSLATION_PROMPT`), kept in the library's `translations` table under `store::translation_key` (text and instructions), so a text is requested once. The window translates the selected paper's title and abstract while `Library::show_translation` is on.
- Batch translation: the marked papers' menu has separate title and abstract actions. `translation::Batch` snapshots and groups the selected texts, counts progress in papers, and skips empty fields; `src/translate.rs` shares cache and in-flight requests with the detail panel and keeps `Settings::translate_workers` batch requests in flight (`Batch::take` / `working`, answers settle in any order; 设置 › AI › 任务, default 4). Stop sends nothing more and keeps the answers already asked for; retry reuses successes. A per-open-library `Arc` rejects late answers after closing/reopening. Debug steps `key:ctrl-a,translate:titles` / `translate:abstracts` exercise the marked selection; `translate:stop` stops it.
- Proxies: `Settings::proxy` is global and applied with `wisp_net::set_proxy` (app start, 设置 › 网络, and `wisp`); `Profile::proxy` overrides it for one model service (`direct` = none) and travels in `HttpRequest::proxy`. Empty everywhere means ureq reads the environment. `settings::proxy_problem` is the address check.
- `ToolDef::writes` marks the tools that change a library (the `WRITING` list); `wisp mcp --read-only` leaves them out, and the chat reloads the library after one ran. `ToolDef::confirm` (the `CONFIRMING` list: the imports, `run_search`, `undo_import`, `remove_search`, `find_pdf`, `organise_papers`, and the two that write a manuscript, `edit_section` and `set_outline`) marks those the window's assistant runs only after the person agreed. The screening decision stays the person's: an agent may propose, never set `screening`.
- Organising (`organise.rs`, tool `organise_papers`): tags added or removed, the star, the reading status and a paragraph added to the notes (marked as the assistant's, never replacing what is there), for any number of papers in one call, written in one transaction (`Store::organise`) or not at all. `organise::apply` changes a paper in memory and says in words what it changed, and nothing where the paper already is as asked; `Store::organise_plan` is the same without writing, which `organise::preview` (`tools::preview_call`) turns into a line per paper for the consent card (`PreparedCall::details`). A call that could not run (a paper not there or in the trash) is not asked about: it fails by itself. `ai::resolve_labels` reads labels in a list of objects too, so `changes[].id` may be `P3`. A new thing an agent may change about held papers goes there; screening and the custom fields stay with their proposing tools.
- The manuscripts are read by `list_manuscripts` and `read_manuscript` and written by `edit_section` and `set_outline` (`tools::MANUSCRIPT`, see `compose.rs`). Those two are in `CONFIRMING`: the window's assistant asks before each (`compose::preview` is the card's lines), except in the conversation that writes that very manuscript (写作's 助手写), where the pen was handed over. An answer also goes into a manuscript by the person's hand: 插入到稿件 under an answer of the library's conversation (`MenuKind::InsertInto`, the sections of the manuscript on the writing page; `Workspace::insert_into_section`) adds it, or what is selected in it, at the end of a section with `Store::append_to_section`, which keeps the section's text as a snapshot first and the citation keys with their papers; `cite::convert_ai_citations` makes the citations the manuscript's.
- Conversations are kept per library, under what they are about (`conversations.paper_id`: empty for the library's, a paper's id, or a manuscript's id for the conversation that writes it; `Library::talk_about`): `conversations` holds an `ai::Transcript` (what was said, and the sources its answers cite) as JSON, `conversation_images` the pictures. What the model read is not kept: a conversation reopened from the history builds its context anew, and `ai::build_context` takes the transcript's sources as `known` so the labels in old answers still name the same papers.
- Full text for writing (`pdftext.rs`, `structure.rs`): `fulltext::file_pages` reads a PDF with hayro's interpreter first (`pdftext::pages`: glyphs with position, size and weight become lines, and a blank line marks every break the page shows, so a heading stands alone; raised citation numbers are left out, ligatures spelled out) and falls back to pdf-extract, which panics on about a third of publisher PDFs. `structure::blocks` turns the page text into paragraphs and headings, `assign_sure` gives each paragraph its part by rule (a heading that names a part, `canonical`; without an "Introduction" the text before the paper's first own heading is the introduction; a review's own headings are `other`; an "Abstract" heading lasts `ABSTRACT_WIDTH` or until a heading of the paper's own, then the part it interrupted goes on) and says where it only guessed, `sentences` cuts the kept paragraphs. A hyphen at a line's end is kept or dropped by the paper's own spelling (`Lexicon::keeps_hyphen`: the compound written elsewhere, the word written whole elsewhere, a gene or a number before it, a closed prefix, and in English two words the paper writes on their own); test a change on real lines both ways. `Store::save_fulltext_pages` does this for every text it keeps: `sentences` rows plus one `structures` row per file (`rules`, `model`, or `none` for a file without text; `open` counts the guessed paragraphs, `paragraphs` all of them, and `StructureInfo::worth_asking` / `structure::worth_asking` is the one place that decides whether a model's look is offered: many guessed, or a good share of a short piece).
- Languages: lengths are counted in `structure::width` (a Chinese, Japanese or Korean letter counts three), sentences end at `。！？．` as well, a sentence or heading may open with a letter of a script without capitals, `canonical` knows the headings of Chinese, Japanese, Korean, German, French, Spanish, Portuguese and Italian papers, and `words` gives character pairs for CJK runs (Latin words keep the stemmer; `OTHER_STOP_WORDS` beside the English ones). Each text's language (`structure::language`, from the script and the commonest words of its kept body text, `body_language`) is the `structures.language` column, `StructureInfo::language`, and `Sentence::language` on every sentence `section_sentences` returns: that is the field to read when choosing sentences by language. The writing page's groundwork line counts the texts per language when there is more than one. In `pdftext`, a page's usual line spacing (`usual_leading`) keeps Chinese set with wide leading in paragraphs, and a numbered title set like the text (`numbered_title`) stands alone. A file without a `structures` row has not been through it: `tools::extract_missing` and `Workspace::extract_missing` read such files again, so libraries from before 写作 catch up on their own; bump `structure::VERSION` when the rules change and `restructure_outdated` redoes the rule-made ones. The abstract is never taken from the PDF: `find_sentences` reads it off the record.
- Candidates: the tool `find_sentences` (part; `query` and/or `queries`; optional paper, `tag`, `starred`; `context` adds the sentence before and after from the same paper and part) ranks the sentences of one part (`retrieval.rs`): each query on its own with BM25 over `structure::words`, against a `retrieval::Index` that `index_for` keeps in memory by a hash of the part's texts (no stored word bags, so a change to `words` needs no migration), the lists merged by reciprocal rank fusion (`fuse`, then at most `PER_PAPER` per paper); without a query it returns how each paper opens the part. `tools::extract_missing` first asks `Store::structure_wanted` and returns at once when every file is sorted. The window and `/write` both go through it; `cargo run --release -p wisp_core --example retrieval_bench` times a search over 4000 made-up sentences.
- Open full texts (`openaccess.rs`, tool `find_pdf`): candidates for a paper come from its arXiv number, from OpenAlex and Europe PMC (asked by DOI or PMID, no key and no address of the asker), and, only when one of the two says the paper is open access, from the publisher's own address for the few publishers that hand a PDF to a plain client (`publisher_candidate`). Nothing logs in or goes round a wall; Europe PMC's own PDF rendering is left out because it answers browsers only. What comes back is kept only if it is a PDF (`is_pdf`), with its origin in `file_origins`. The tools take a second function for this, `sources::Download`, beside `Fetch`. In the window it is a run like the import's (`Library::fetching`, `fetch_start` / `fetch_next`).
- Completing by title (`complete.rs`, tool `find_metadata`, 按题目补全 in the detail panel for a paper with neither DOI nor PMID): `complete::find` asks Crossref, Europe PMC and arXiv for records by title (`PER_SOURCE` each), reports each source on its own (`Asked`: found, nothing, or why it failed), makes records of one DOI one `Candidate` and orders them by `similarity` (words in the same order; 1 only for the same title). The title asked for is the paper's, or, while that is the name of its file (`placeholder_title`), the one its first page shows (`pdftext::title_guess`), for the person to correct. Nothing is written by the tool or by a model: the window (`Modal::Complete`, `complete_find` / `complete_apply`) has the person pick a record and its fields; `complete::suggested` is what is ticked beforehand (blank fields, a title that is a file name) and only for a record at least `ALIKE_ENOUGH` like the title; a record the library holds as another paper is refused. There is no browser bridge and none is wanted: sources are asked over HTTP like every other lookup.
- Quotations are checked: `ai::check_quote` looks a quotation up in the stored page text (`Quoted`: found, elsewhere, only its beginning, missing, no text), `Library::check_quotes` does it for the finished answers of a conversation, the chips say the result. `ai::citation_spans` is where an answer cites, for the clickable citations in the text.
- `sources.rs` searches PubMed, Europe PMC, Crossref and arXiv (PubMed and arXiv answer in XML, read by the small `elements` helper). A saved search is a `searches` row; each run is an `import_batches` row with its papers in `batch_papers`, which is what `undo_batch` removes (untouched papers only).

### `crates/cli` (`wisp_cli`): the `wisp` binary

A thin shell over `tools` and `mcp`: argument words in, JSON out; `wisp mcp` is newline-delimited JSON-RPC on stdin/stdout. It is a separate binary because the app is a Windows GUI-subsystem program with no console. It opens the same data folder as the app (`settings::default_root` / `settings_file`), possibly while the app is running.

### Root crate (`wisp_paper`): the GPUI app

- `src/app.rs` holds all state in one root view, `Workspace` (`lib: Option<Library>` is the open library, `None` is the home page). Every click is a `Cmd` enum value, wired with `self.on(Cmd::…, cx)` and handled in `Workspace::run`. Popup menus are built from a `MenuKind` in `open_menu`; dialogs are `Modal` variants, built and submitted in `app.rs`.
- `home.rs`, `library.rs`, `detail.rs`, `chat.rs`, `dialogs.rs` are `impl Workspace` blocks that only render. A new feature usually means: a `Cmd` variant, its arm in `run`, and the element that emits it.
- Store writes go through `Workspace::change`, which runs the closure, calls `Library::reload` (re-reads papers, fields, files, trash and refilters) and shows a toast on failure. `Library::shown` is indices into `papers`, recomputed by `refilter`.
- Background work (PDF text extraction, lookups, chat streaming) runs on `cx.background_executor()` and comes back through `this.update`. Each task captures the library id (chats also a `generation` counter) and stops when the user has since closed the library or started a new conversation; keep that check in new async code.
- A library question's scope is the currently shown list (`lib.shown`), so view, search and filters change what the model reads up front. The context is built once with the first question of a conversation. The panel behind 文献 in the conversation's header (`render_materials` in `chat.rs`, `Chat::materials_open`) floats over the conversation and pushes nothing down; a press beside it or Esc puts it away. Before the first question its search box (`Library::scope_find`, the words in `scope_words`, the papers holding them in `scope_hits`, made anew by `scope_refilter` with the words and with every `refilter`: a frame does not search abstracts) narrows the list and the scope with it (`Library::scope_listed`). A row dragged into the conversation (GPUI's `on_drag` with a `chat::PaperDrag`, dropped anywhere under the header; `Workspace::pinning` while it is held) or its plus keeps the question to that paper: it joins `Library::asked`, the same list 就这 N 篇提问 fills, shown as chips over the question box that let each go again (`Cmd::Scope(ScopeDo)`). `Library::scope_papers` is the one place that says what the scope is (`ask` reads the same fields); a new conversation empties both (`scope_reset`), and once the material is built the panel lists what was handed over and nothing can be picked. `Workspace::save_chat` keeps the conversation in the library after the question and after the answer; 历史 lists them (`Chat::history`) and `open_chat` takes one up again.
- A library has three conversations, told apart by `Talk`: `Library` (助手, `library_chat`), `Paper` (the selected paper's, `paper_chat`) and `Write` (the one that writes the manuscript, `write_chat`). Every function and command of the chat takes a `Talk`; `chat_of!(lib, talk)` borrows the one meant alone, so the rest of the library can be read meanwhile. What only the library's conversation has (the scope panel, reviews, 插入到稿件) is asked as `talk == Talk::Library`, not as "not the paper's".
- The chat is an agent loop (`ask` → `chat_step` → `run_tools` → `execute_tools` → `chat_step` …, at most `MAX_CHAT_STEPS` requests per question; before the last one the results carry `ai::LAST_STEP_NOTE`, telling the model to answer with what it has). `Chat::wire` is the conversation in the protocol's own messages and is append-only: the model's turns go back exactly as received (`ai::TurnReader` keeps thinking blocks and their signatures), and every tool call gets a result even when it did not run: refused by the person (`Chat::pending`, `Cmd::AnswerTools`), or stopped (`stop_chat`, which also keeps the text so far as the model's turn). Tools run on the background executor, each call with its own `Store` connection: a turn that only reads runs its calls side by side, one that writes runs them in order. `wisp_net::stream_chat` sends a request again, up to twice, when the service is busy (408, 409, 429, 5xx) or unreachable. Papers are named to the model by label (`P3`): `ai::resolve_labels` on the way in, `ai::add_labels` on the way out.
- A question may carry pictures (`ChatItem::User::images`, pasted into the box or picked): `picture::prepare` makes each one a model takes (PNG, JPEG, GIF, WebP; scaled down when large), `ai::user_message_with` writes them the way each protocol wants.
- 写作 (`src/write.rs` renders the editor and the candidates; `src/manuscripts.rs` the manuscripts; state in `Writing`): a library holds any number of manuscripts (`wisp_core::manuscript`: tables `manuscripts`, `manuscript_sections`, `section_snapshots`, with the `Store` methods in that file). A manuscript has a title, a language (`Writing::language`, a code of `manuscript::LANGUAGES`, default `en`) and ordered sections; a section has the person's name and a `kind`, a key of `structure::SECTIONS`, which is the part the candidates come from (`Writing::kind`; `other` for a review's own sections). A new one starts with IMRaD named in its language (`manuscript::imrad`). A section's text is saved as it is typed (`Workspace::write_typed`); a snapshot is kept `PAUSE_SECS` after the last key and on leaving the section (`write_snapshot`), only when `manuscript::worth_keeping`, at most `KEEP_SNAPSHOTS`; restoring one (`Store::restore_snapshot`) first keeps the current text. A removed manuscript is only marked (`removed_at`); a removed section goes with its snapshots, after a confirmation when it has text. Export (`manuscript::markdown`, `plain_text` for 复制全文, `docx`, a hand-written zip with stored entries) leaves out empty sections. The `drafts` table of earlier builds is emptied into one manuscript (`早先的草稿`) by `manuscript::migrate_drafts` on every open, so what an older build writes there comes in as another one; the schema version stays, since an older build reads the rest as before. Candidates are asked for, not looked up while typing (`src/write_find.rs`, `CandidateSearch`): the shortcut `write-find` (⌘↩ / Ctrl+Enter) or the panel's button searches for the selection, else the paragraph at the caret (`retrieval::paragraph_at`); the find box searches on Enter, its words as typed when they are plain Latin. Only the list of how each paper opens the part comes by itself (`write_openers`, when a part is opened), and texts read or sorted anew refresh only that list (`write_texts_changed`). What is written, in any language, is made by the translation model into three to five groups of search words in the sentences' language (`retrieval::queries_system` / `parse_groups`: content, rhetorical move, other wordings; cached per language and text in `CandidateSearch::made`), shown under the find box; without a model the words go as written and the panel says so. The part and the sentences' language are read through `Writing::kind` and `Library::sentences_language`. The `other` part is offered when some text has sentences there; the candidates can be narrowed to a tag or the starred papers, and a card unfolds into its neighbours. The model's part in the groundwork is a run like the screening one (`write_run_start` / `write_run_next`, `Task::Structure`): sorting asks about a text's outline (`structure::outline_prompt` / `parse_outline`) only for files whose rules left `OPEN_ENOUGH` paragraphs guessed, and `structure::merge` keeps the rules' labels where they were sure; reading sends each page of a file without text as a picture (`pdf::page_pictures`, `ai::read_page_request`), at most `READ_PAGES` per run, and keeps the text with `Store::save_read_pages`, which records who read it in `structures.text_by` and how many of how many pages in `pages_read` / `page_count`: a file read in part (`StructureInfo::read_in_part`) says so in the run's result and the detail panel, and the next run goes on from the first page not read. One request at a time; a new part (`Assisting::leave`), library or request drops what is in flight. The manuscript's language is `Workspace::manuscript_language`, English until the manuscript carries one.

- Citations in 写作 (`wisp_core::cite`, window side `src/cite.rs`, state `Library::citing`): written in Pandoc's form `[@Zhang2024]` (`[@A; @B]`, with locators), so a draft and its exported Markdown stay plain text and Pandoc formats them with the BibTeX of the cited papers (`cite::bibtex`, same keys, through `export::bibtex_keyed`). A key is first author + year (`DeNovo2020` from the title without authors, `-nd` without a year), a letter for the second paper with the same key; `cite::Index` gives them in the order papers were added, so a new paper never takes an earlier one's key, and a key once cited is kept in `cite_keys` (`Store::keep_cite_key`) so it stays with its paper when the record changes or another is deleted. `cite::find` resolves every citation of a text (`Found`: paper, trashed, removed, unknown, or ambiguous for the old `(Zhang et al., 2021)` form, which is still read and `cite::upgrades` rewrites into keys); `cite::references` is the list in author-year order, `reference_list` / `reference_markdown` its text. - 出处 (`src/write_source.rs`, state `Citing::sources`, a `Sourcing`; every command is `Cmd::Source(Do)`): `cite::Listed::standing` is every citation of the manuscript with the passage kept for it (`standing`, a `Standing` with its `Rests`), worked out by `cite_refresh` with the rest. - 综述 (`wisp_core::review`, window side in `src/chat.rs`): `/review` gives the conversation with the library a record (`review_projects`, one JSON body with a `revision`; `review_conversations` ties it to its conversation, and it goes with it: `Store::remove_conversation`, and the schema batch clears one left behind). `Review::step` is where it stands (1 the requirements, 2 the framework, 3 the outline, 4 writing); `ReviewAction` is every change, applied by `Store::apply_review` against the revision the caller read. A text field with the keyboard hears them first; a one-line or empty field passes Up and Down on. A right click is `.on_mouse_down(MouseButton::Right, self.on_context(MenuKind::…, cx))`, its items in `context_menu` (`Menu::breaks` are the lines between groups, `Menu::paper` the row marked meanwhile): papers, trashed papers, files, tags (rename and remove: `Workspace::retag`), past conversations, answers.
- Several papers at once (`Library::marked`, 全部文献 only): a click with ⌘ / Ctrl adds or takes one (`Workspace::mark`), with Shift the stretch from `Library::anchor`; Shift with an arrow moves `Library::cursor`, ⌘A marks the list on show, Esc lets go. More than one marked puts the detail panel away, and showing one paper (`select`) ends the marking. A right click on a marked row is `MenuKind::Papers`; its commands end in `Workspace::run_batch` (`AskPapers`, `StarPapers`, `ReadPapers`, `TagPapers`, `FindPdfsOf`, `AskTrashPapers` / `TrashPapers`). `AskPapers` starts a new conversation with the library about those papers alone: `Library::asked`, read through `Library::scope_papers` wherever the scope of a library question is shown or built, and emptied by the next new conversation.
- Text that is not an answer or a field is selected through `Workspace::selectable(key, text, cx)` (`src/select.rs`, `Workspace::picked`): drag, double click for a word, triple for all, ⌘C or a right click to copy. While the button is held a layer over the window follows the pointer, as for the edges. Use it for any text a reader may want to copy.
- The detail panel's width is `Settings::detail_width` (0 is `DETAIL_W`), dragged by its left edge (`detail.rs`). An element only hears the pointer moving over itself, so while an edge is held (`Workspace::resizing`, an `Edge`) a layer over the whole window takes the moves (`home.rs`); do the same for any other drag. A tap is over before that layer is drawn, so each edge also hears its own mouse-up.
- The library's sidebar is `Settings::sidebar_width` (0 is `SIDEBAR_W`) and `Settings::sidebar_hidden`: its right edge is dragged (`Workspace::drag_sidebar`; pulled in past half of `SIDEBAR_MIN` it is put away, back out and it returns), clicked twice it is put away, and `Cmd::ToggleSidebar` (the button at the top left, the shortcut `sidebar`) puts it away or brings it back. Widths are computed from `Workspace::sidebar_width`, never from the constant. The two top-left buttons (`render_corner`) are drawn in the sidebar or, while it is away, over the list at the same place, level with macOS's traffic lights.
- Reading mode (`Library::reading`, `Cmd::ToggleReading`: the button on the PDF's toolbar, the shortcut `reading`, Esc to leave before Esc closes the paper): `detail_width` is then the window's and `render_library` draws the detail panel alone, with a one-line header and no left edge. Nothing is made anew, so `Library::pdf` keeps its place and `paper_chat` its conversation and unsent text; leaving the paper, changing the page or the search shortcut ends it. The conversation's width beside the PDF is `Settings::chat_width` (0 is a share of the panel; `Workspace::chat_width`, `split_chat_width` in `library.rs`), dragged by the edge between the two (`Edge::Split`, `drag_split`).
- `PdfView` draws pages at `Zoom` (fit width, fit page, or a percentage of the page's own size). `resize` is the one place that changes what decides the page size and keeps the point under an anchor where it was; pages are rendered at `render_scale` (a few steps, within `MAX_PAGE_PIXELS`) and kept within `KEEP_BYTES`. The wheel is heard in the capture phase by a canvas under the list (`PdfView::wheel`), since the list would scroll before a parent could zoom.
- Asking about a paper lays the window out for it (`Workspace::asking`, in `library.rs`): the sidebar is away, the papers on show are a narrow list at the left (`render_ask_list`: the corner's two buttons, the search box, a two-line title and a line of details per paper; `Settings::ask_list_width`, 0 is `ASK_LIST_W`, dragged by the detail panel's left edge), and the conversation with the paper's PDF to its right has the rest (`detail_width`). Nothing is stored for it: it follows from 提问 being the tab and `Library::split` (on by default; `Cmd::BesidePdf`, the x on the PDF's bar puts the PDF away and so ends it for the papers after as well, 对照 PDF brings it back). `Cmd::LeaveAsk` (Esc before Esc closes the paper, 退出提问 in the one-line header, the sidebar's button or shortcut) goes back to the tab it was come to from (`Library::ask_from`). On a page whose list is not the papers' (筛选, 助手, 写作), or in a window narrower than `ASK_LIST_MIN` + `detail::SPLIT_MIN`, there is no list and the paper has the window. A paper without a PDF keeps the layout, with 添加 PDF / 查找开放全文 at the right, so the arrow keys do not change the layout from paper to paper. The table and the narrow list share `Library::table_scroll`; `render_library` scrolls to the selected paper when the layout changes (`Library::ask_drawn`), and row heights come from `Workspace::row_height`. A citation followed from that conversation, a passage or a picture sent from the PDF, all end there.
- The paper's conversation can float over its PDF instead (`src/floating.rs`, `Settings::floating`, the geometry in `wisp_core::floating`): where the conversation would stand beside the PDF, the PDF takes the whole panel and the same `Chat` and input are drawn in a window over it (the PDF's bar of tools stays clear). The title bar moves it, the bottom-right corner sizes it (`MIN_WIDTH` / `MIN_HEIGHT`), 分栏 goes back beside, the minus folds it into a round button that a drag moves and a click opens (`is_drag`: farther than `DRAG_SLOP`). Place, size and folding are saved; `fit` keeps what is drawn inside the area, which is measured as it is drawn (`Library::float_area`), and leaves the stored place alone, so a window grown back finds it. A held title bar, corner or button is `Library::float_drag`, heard by a layer over the whole window (`render_float_layer`, drawn in home.rs) like the edges. The window and button `occlude()`, so the PDF under them hears neither wheel nor press while the rest of it scrolls and selects as before. A passage or picture sent from the PDF opens a folded conversation (`unfold_chat` in `show_paper_chat`). The switch to floating is 悬浮 in the conversation's header (`render_float_switch`).
- Selecting in a PDF: the worker hands out a page's glyphs (`pdftext::page_marks`, after the page is drawn), `PdfView` keeps a `Selection` of them on one page (`mark_at`, `mark_boxes`, `marks_text` in core), and tells its owner through `PdfEvent` (copied; a passage for a conversation, kept in `Chat::quotes` and written into the question as `[P3 p.5 "…"]` by `ai::quoted_passage`; a piece of a page cut out as a picture; a passage to translate). 翻译 puts a card by the selection (`card_place` keeps it in view): `Workspace::translate_passage` goes through `translate_text` (`src/translate.rs`), the same path and cache as the title and abstract and the batch, and `sync_pdf_translation` hands the state back (`PdfView::show_translation`). Its menu asks one of `Settings::profiles()` for this once, without changing the settings, and that answer replaces the kept one (`Store::replace_translation`; the cache key has no model in it); `Library::translation_asks` drops an answer that a later request for the same text overtook.
- Selecting in an answer: `markdown::render` takes a `Selecting`, keeps the `TextLayout` of every piece it draws and reports where the pointer is as a `Place` (piece, byte); the selection is `Chat::picked`, its text `markdown::text_between`.
- A window that is not on screen draws no frames: in a scripted run, pointer steps need a `shot:` before them, or there are no hitboxes to hit.
- The manuscript editor draws Markdown as it says (`TextInput::markdown`, like quiet-md's editor but keeping the text as written): `wisp_core::markdown::lines` reads each line with its pieces and where their syntax is (`Piece`, `Part`; `inline` is built on the same reader), `shape_markdown` in `input.rs` shapes one row per line (headings larger, emphasis, code, links and `[@Key]` citations in their style, a dot for `-`, quotes behind a bar, a ground for fenced code, a line for `---`) and hides the syntax except on the lines the selection or caret is on (held while the button is down). `DisplayMap` is how drawn offsets stand to the text's bytes; every hit test, caret, selection, IME rectangle and comment tint goes through it. Enter in a list or quote goes on with it (`markdown::continued`), on an empty item ends it. A section's text is therefore Markdown everywhere: `manuscript::section_markdown` (headings written in a section go under the section's) is the export and what 通读 and the versions draw, `markdown::plain` is the clipboard's and a Word file's text, a new Word file gets the bold, italic and headings (`word_paragraph`), and a Word file's paragraph that would read as Markdown comes in escaped (`escape_markdown`).
- What a click selects in a text field is `wisp_core::selection`: two clicks a word (ICU4X's `icu_segmenter` with its dictionaries, so Chinese and Japanese come apart into words; single Han characters next to each other, an unknown term, are taken together up to a word in `JOINING`; a `[@…]` citation is one word), ⌘ / Ctrl with a click the sentence (`citefind::whole_sentences`: cut as 配引用 cuts, but a semicolon goes on), three the paragraph (the line without its quote, marker or hashes). `TextInput::grain` keeps the unit, and a drag after the press grows the selection by it (`selection::extend`). A masked field selects all.
- `input.rs` is the app's own text input (single / multi-line, IME via `EntityInputHandler`; a field that `accepts_images` hands pasted pictures to its owner; Cmd/Ctrl+Z and Shift+Z undo and redo, letters typed in a row being one step; `replace_range` is an owner's change as one step); `pdf.rs` renders pages with `hayro` on a worker thread into a virtualised list, keeping a bounded number of pages.
- `build.rs` embeds every file under `assets/` (of `branding/`, only `app-icon.png`) into the binary; icons are loaded by name through `ui::icon`. On Windows it also compiles the icon resource.

### `site/`: the project page

https://xuzhougeng.github.io/WispPaper/ is three hand-written files (`index.html`, `style.css`, `site.js`), no generator and nothing loaded from another host (no web fonts: the stacks are system ones). `site/build.sh [folder]` adds the screenshots from `docs/images` and the icon; `python3 -m http.server --directory dist/site` shows the result. `.github/workflows/pages.yml` deploys it on a push to main that touches it and after every published release, writing `release.json` (the latest release's files) next to the page: the download buttons read it, and lead to the release page without it. The page is laid out as a paper (numbered figures, citations that can be clicked); its numbers are those of `docs/TUTORIAL.md`, and its colours are `theme.rs`'s. Keep it out of `scripts/`, whose changes rehearse the packaging.

### `vendor/`

`gpui` 0.2.2, `taffy` 0.9.0 and `xattr` 0.2.3 are vendored with local patches and wired in through `[patch.crates-io]`. Patched spots carry a `quiet.md:` comment and are listed in `vendor/PATCHES.md`. GPUI APIs here are 0.2.2 plus those patches (for example `grid_col_widths`, `ListState::estimated_scroll_metrics`), so check `vendor/gpui/src` rather than upstream docs.

## Scope

Ported from BiblioCell, without its datasets and web version. Being added step by step: the tool layer with CLI and MCP (done, read-only tools), the chat as an agent loop over the tools with `/search` and `/cite` (done), search sources with trial queries and batch import (done: 检索与导入 page, `src/searches.rs`), a guide page for a new library that starts from a search (done: `src/guide.rs`; `ai::query_prompt` / `parse_queries` ask the model for queries per database, each is tried with `search_online`, the person picks), AI screening suggestions that the person confirms (鲸吞法: import broadly by query, let the agent judge, the person decides; done: 筛选 page in `src/screen.rs`, with 逐篇 and 确认 beside it, `screening_suggestions` table, `ai::screen_prompt` / `parse_judgement`, tool `suggest_screening`), scheduled source sync (done: `LibraryInfo::auto_sync_hours`, tool `sync_searches` with `tools::due_searches`, `Workspace::watch_searches` looks once a minute), and jumping to the quoted sentence in the PDF (done: the assistant may cite `[P3 p.5 "a sentence"]`, parsed by `ai::citations`; `PdfView::find` has the worker interpret the page with a glyph-collecting hayro `Device`, and `fulltext::find_quote` / `line_boxes` turn the match into one box per line, drawn over the page image). That roadmap is complete; what each step left out is in its pull request (2 to 8). After it: 写作, a writing page whose advantage is candidate sentences from the same part of the library's papers, on top of PDFs read with their layout and sorted into parts (rules first, a model where no heading says, a model's eyes for scans). Then 图片库, after CiteBox's figure library: figures and tables cut out of the PDFs and kept with their legend, tags and notes, entered from 收藏. Then 批注: a manuscript can start from a Word or Markdown file or from what the assistant wrote, the assistant reviews it with comments as in Word's review, and the export goes back into the Word file with comments and, when asked, tracked changes. Left out of that step: tables and pictures are not shown in the editor (they stay in the file), text inside tables cannot be changed, a comment that came with a file cannot be removed or replied to, and a paragraph moved to another place loses its inline formatting. Then 改稿: a box under the manuscript where the assistant is told what to change in the section and changes it there, each change shown where it is made and taken back at will. Then 生图: providers can hold models that draw (OpenAI, Gemini, 火山方舟's Seedream, or any relay through one of three interfaces), and 图片库 has a picture drawn from a description and keeps it. Left out of that step: a picture is drawn from words alone (no reference picture, no editing of one that exists), one at a time, and the assistant has no tool for it. With it, 判断: a provider for System One models (TypeSafe's Jev), which decide among given answers and write nothing, and which 批量筛选 can be handed to. Left out: 提取's Select fields, the checking of quotations and the guide's choices could be asked of such a model too and are not yet; its `score`, `noul` and `box` questions are not used. Then 出处: a citation keeps the sentence of its paper it rests on (kept when citing from a candidate, from 配引用 or from an answer; looked for afterwards in the cited paper by search and a model), shown under the entries of the reference page and, for the citation the caret is in, under the manuscript, and opened in the PDF. Left out of that step: choosing another sentence of the paper by hand (cite from a candidate of 找句子 instead), a passage per citation is one sentence, and nothing of it goes into an exported file. Then 助手写: 写作 has two modes to switch between, the person's own writing as before, and one where the assistant leads: the outline at the left, the conversation in the middle, the manuscript at the right, which the assistant writes with `edit_section` and `set_outline` while the person reads, corrects and steps back through each section's versions. Left out of that step: the words appear when a tool call is complete, not while the model writes them (改稿 shows them as they come); a version is a section's, not the whole manuscript's, and is shown as it was, without what differs from now; the assistant cannot remove a section that has text or move text between sections but by rewriting both; and the candidates panel is not shown in this mode. API keys are stored in plain text in `settings.json`; when empty, `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` are read from the environment.
